# Задача: надёжность и удобство MCP-интерфейса и skills

Дата: 2026-10-18. Статус: реализация начата; итоговая приёмка не выполнена. Прогресс и фиксированная матрица критериев — в [отчёте приёмки](mcp-skills-hardening-acceptance.md).

Основание: совместное ревью MCP и двух skills тремя субагентами по
`mcp-server-best-practices` и `agent-skills-best-practices`, сверка
[справочника системы](system-and-tools-reference.md) с кодом ревизии
`a3e0baea4396a30fa6902cea6b831bfe39956001`.

## 1. Результат и границы

Устранить возможность незавершённой обработки Events из-за гонки доставки,
сохранить доступность чтения при большом объёме coverage, дать ограниченный
путь чтения полного текста через tools, улучшить обнаружение инструментов,
диагностику и сопровождение контрактов. Актуализировать документацию и skills
по фактически принятой реализации.

Сохранить единый Go-service с внутренним collector, HTTP MCP и STDIO-мостом,
текущую сессию, корпус, архивы, подписки, checkpoints и результаты операций.
Обычное чтение, обработка Events и journal ack не отмечают сообщения прочитанными
и не меняют реакции. Действующие разрешения на отправку/read/react не расширять.

Это задача по серверу и клиентским инструкциям, не переход на другую архитектуру
или обязательная миграция протокола. Не добавлять Tasks, Apps, Prompts, новый
collector, туннель или отдельный action skill ради покрытия возможностей MCP.
Не удалять legacy API и не пересоздавать рабочие подписки. Новые модельные evals
и повторные live-записи в Zalo в базовую приёмку не входят.

улучшение удобства/сопровождения. Пункты ниже входят в объём задачи; приоритет
задаёт порядок, а не разрешение оставить пункт незавершённым.

| R02 | P2 | Ограниченное coverage и доступные страницы сообщений | Большая история gaps не блокирует короткое сообщение; подробности покрытия доступны с продолжением |

## 3. Контракты — до реализации

Сначала подготовить таблицу изменений JSON Schema, примеры успешных/ошибочных
ответов и стратегию совместимости. Зафиксировать имена, типы, обязательность,
nullable/default, лимиты, порядок, единицы измерения и срок жизни курсоров.
Предлагаемые ниже имена новых полей и tools — проект контракта, не утверждение,
что они уже опубликованы. Окончательное решение закрепить в docs/contracts.

Добавление поля не считать автоматически совместимым: проверить старые строгие
схемы, сохранённые задания и целевые клиенты. Если изменение ломает согласованный
публичный контракт, подготовить конкретный вариант версионирования и согласовать
его перед реализацией. Не менять исторические payload и outcomes задним числом.

### R01. Events: блокировка и продолжение

Основание: `worker.go` сохраняет delivered после ответа receiver;
`storage/event_journal.go` блокирует pending/sending; оба event references сейчас
предписывают закончить запуск при blocked_on_delivery. Это возможная
последовательность по коду, не установленная причина прежних live-инцидентов.

- Дополнить результат `zalo_read_subscription_events` безопасной подсказкой
  продолжения: например, nullable `retry_after_ms` и причиной блокировки из
  закрытого списка. Указать семантику has_more при блокировке.
- Сохранить упорядоченный журнал, HMAC receipts, generation/principal checks и
  запрет подтверждения ещё не обработанных записей. Не обходить гонку выдачей
  sending как уже доставленного события или фиктивным ack.
- Определить ограниченные повторные чтения и устойчивую точку продолжения
  после исчерпания попыток, отмены или перезапуска агента. Ограниченный retry сам
  по себе не гарантирует продолжение: нужен проверенный механизм host либо
  отдельно спроектированный recovery wakeup с подавлением повторов.
- Сначала исследовать доступные возможности целевого host; выбранный механизм
  описать отдельным решением. Если host не поддерживает продолжение, вернуть
  явный неподдерживаемый режим; такая конфигурация не проходит критерий R01.
- Не использовать бесконечный polling и не обещать exactly-once уведомление:
  разрыв между внешним уведомлением и ack остаётся отдельным ограничением.

Приёмка: receiver запускает чтение до HTTP 2xx, а также между 2xx и сохранением
delivered. Без новых сообщений workflow возобновляется, читает ту же запись и
подтверждает её после успеха. Проверить длительную блокировку сверх retry-окна,
перезапуск, повторное пробуждение, ошибку receiver, отмену подписки и отсутствие
busy loop. Синтетический receiver и harness не отправляют сообщений в Zalo.

### R02. Coverage и бюджет ответа

- Определить компактный summary покрытия с полным количеством gaps,
  признаком усечения и проверяемым продолжением подробностей.
- Подробности читать постранично через согласованный tool/resource; сохранить
  ограничения доступа, интервалы, времена наблюдения и честную неполноту.
- Согласовать миграцию прежнего поля gaps: нельзя молча заменить полный список
  частичным, сохранив прежнее обещание полноты.
- Для corpus browse уменьшать размер страницы до бюджета с корректным cursor,
  не пропуская и не дублируя строки; поведение при неудаляемом oversized item
  должно давать конкретный безопасный следующий шаг.

Приёмка: короткий anchor с before=0/after=0 читается при 800 и более gaps;
поиск и browse также доступны. Пагинация подробностей даёт все разрешённые gaps
в пределах заявленного snapshot/retention-контракта. Ответы укладываются в бюджет,
coverage не теряется молча. Существующий тест RESPONSE_TOO_LARGE обновить по
новому поведению, сохранив проверки действительно недопустимого размера.

### R03. Полный текст без зависимости от resources

- Предложить bounded content-read tool (рабочее имя
  `zalo_read_message_content`) для retained typed messages и сохранённого архива.
  Не смешивать archive_row_id с message ID; вместо произвольных URL использовать
  точную typed identity или непрозрачный handle, выданный сервером.
- Определить cursor/limit, единицы длины Unicode, maximum bytes, has_more,
  next_cursor, text provenance и доступность. Курсор связывает цель и представление;
  каждая страница повторно проверяет policy, retention, recall и доступ к архиву.
- Дать различимые ошибки неверной цели, истёкшего курсора, недоступных данных,
  отказа доступа и oversized projection без утечки приватных полей.
- Сохранить действующие resources; унифицировать ResourceLink для typed context
  там, где это помогает клиенту. Не загружать media bytes или внешние URL.

Приёмка: клиенту с tools-only доступны длинный Unicode-текст корпуса и текст
архива без пропусков/повторов; для клиента с resources прежний путь работает.
Проверить пустой текст, текст на границе лимита, отзыв доступа/recall между
страницами, неподходящий ID и отсутствие любых upstream write-действий.

### R06–R08. Схемы, сборка и диагностика

- R06: удалять только недостижимые `$defs` по транзитивным локальным `$ref`,
  учитывая композиции, циклы и escaping JSON Pointer. Не менять валидаторную
  семантику. Обновить manifest/baselines и зафиксировать размер до/после.
  Ориентир аудита: 37 880 лишних байт из 124 708 байт схем; это не обещание
  эквивалентного уменьшения токенов каждого host.
- R07: единый безопасный build identity для service и bridge — версия,
  revision, dirty flag, с явным unknown при отсутствии build metadata.
  STDIO должен позволять отличить сборку моста от обслуживающего backend.
  Не выдавать локальные пути сборки; protocolVersion остаётся отдельным полем.
- R08: добавить nullable `delivery_reason` из закрытого списка, сохранив
  совместимую семантику gap_reason. Определить устойчивый неприватный delivery
  reference и отдельный attempt ID; связать retry/restart с журналом и логом.
  Для ошибок tools создать correlation ID до выполнения и вернуть его в
  согласованном details/_meta вместе с записью в логе.
- Разделить локальную диагностику и внешнюю telemetry. Не публиковать payload,
  callback URL, токены, signing keys, native account/message IDs или raw errors.
  Не превращать уникальные ID в высококардинальные labels метрик.

Приёмка: прежние валидные/невалидные fixtures сохраняют результат валидации;
недостижимых definitions нет. HTTP и STDIO сообщают проверенную идентичность
сборок. Причины queue capacity/deadline/attempts/rejection различимы; retry и
restart сохраняют связь доставки, попытки различаются. Ошибка клиента связана
с конкретным логом, проверки редактирования секретов проходят.

## 6. Итоговая приёмка двумя независимыми субагентами

После реализации назначить **двух независимых субагентов-рецензентов**.
Первый делает акцент на контрактах/коде/совместимости, второй — на сценариях,
доказательствах, документации, skills и установленной версии. **Каждый проверяет
весь объём R01–R12**, а не только свою специализацию. Первый verdict второго
не подсказывать; после независимых отчётов устранить замечания и повторить ревью.

До реализации разложить R01–R12 на проверяемые критерии из этого документа и
зафиксировать их список в отчёте приёмки. Для каждого критерия: источник,
ожидаемый результат, фактическое доказательство и PASS/FAIL/NOT_RUN.

Полнота каждого reviewer = число PASS / общее число обязательных критериев × 100%.
FAIL и NOT_RUN не считаются выполнением; частичный пункт не округлять до PASS.
Не сокращать знаменатель и не объявлять требование N/A для получения 100%.
Изменение scope требует отдельного согласования пользователя до финального verdict.

У каждого reviewer итог должен содержать:

- проверенную Git revision и соответствие установленного backend;
- полноту в процентах и таблицу доказательств по всем R;
- число нерешённых ошибок с серьёзностью и точными ссылками;
- границы проверки и оставшиеся документированные ограничения;
- однозначный verdict ACCEPTED / NOT ACCEPTED.

**Gate завершения: оба независимо подтверждают 100% полноты и 0 нерешённых
ошибок любой серьёзности в согласованном объёме; обязательные проверки и CI
зелёные.** После изменения принятой ревизии проверить затронутые критерии заново
и обновить оба verdict. Ноль обнаруженных ошибок не объявлять математической
гарантией отсутствия любых дефектов вне проверенного объёма.

## 7. Готовый goal

Реализовать и проверить улучшения zl-mcp по
`docs/task-mcp-skills-hardening.md` (R01–R12), начиная с контрактов: устранить
гонку доставки и обеспечить возобновление обработки последнего Events-события,
отделить объёмное coverage от чтения сообщений, добавить ограниченное чтение
