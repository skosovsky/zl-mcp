# Задача: прямой запуск Go-collector через launchd

Дата: 1 октября 2026 года. Статус: заменена задачей [единого сервиса для Ann](task-unified-ann-service.md), реализация не начата.

Не выполнять эту задачу отдельно: согласована архитектура одного постоянного Go-процесса с внутренним collector, MCP-интерфейсом и доставкой событий. Требования к логам, auth_required и миграции перенесены в новую задачу; текст ниже сохранён как предыдущее направление.

## Проблема и результат

Сейчас LaunchAgent запускает Python-обвязку, которая управляет Go-collector, ротирует логи и останавливает перезапуски при необходимости нового входа. macOS отображает фоновую активность как `python3`. Обвязка добавляет зависимость и дублирует управление процессом.

Результат задачи: один установленный Go-бинарник `zl-mcp`, напрямую запускаемый пользовательским launchd. Collector самостоятельно ведёт ограниченные файловые логи и при потере авторизации остаётся доступным для диагностики без сетевых повторов. Python-обвязка удалена после проверки нового сервиса.

Исходный checkout остаётся в iCloud. Рабочие бинарник, конфиг, состояние и логи сохраняют согласованные локальные пути из [mac-deployment.md](mac-deployment.md). Сессия, SQLite, allowlist и операции вступления сохраняются.

## Разделение ответственности

| Компонент | Ответственность |
|---|---|
| launchd | Запуск collector после входа пользователя в macOS, восстановление после падения |
| Collector | Соединение, reconnect при сетевых сбоях, состояние авторизации, heartbeat, control socket, SIGTERM |
| Go-логирование | JSON-логи, ротация, закрытие файлов, private permissions |
| MCP-клиент | Запуск `zl-mcp serve` по stdio |

Отдельный supervisor и второй управляющий бинарник не нужны. Работа до входа пользователя, сбор во время сна и гарантия полного replay не входят в задачу.

## Контракт до реализации

Сначала обновить ТЗ, пример конфига и описание CLI. Новые MCP tools и изменения существующих JSON Schemas не требуются: `auth_required` уже входит в status.

Чтобы сохранить существующее поведение интерактивного CLI, явно выделить сервисный режим ожидания. Предлагаемый конфигурационный контракт:

```toml
[collection]
auth_required_behavior = "wait" # допустимы exit и wait; по умолчанию exit

[logging]
level = "info"
file = "/Users/USERNAME/Library/Logs/zl-mcp/collector.log"
max_size_mb = 5
max_backups = 3
```

`group_ids` и остальные действующие настройки сохраняются. `exit` сохраняет прежнее завершение collector при auth failure; установленный LaunchAgent использует `wait`. Параметры ротации имеют значения по умолчанию 5 МиБ и три архива; неверные значения и неизвестный режим отклоняются. Отсутствие `logging.file` сохраняет stderr. Файловый sink применяется к `collect`; `serve` продолжает писать диагностику в stderr, stdout содержит только MCP.

## Поведение при auth_required

В режиме `wait` обработать оба пути: отказ saved-session Restore при запуске и потерю авторизации уже подключённого listener.

1. Сохранить `authenticated=false`, `collector_state=auth_required`, `last_error.code=NOT_AUTHENTICATED` и known gap.
2. Прекратить listener, reconnect, обновление каталога и остальные сетевые обращения к Zalo. Не создавать новый QR и не перечитывать сессию по таймеру.
3. Сохранить процесс, эксклюзивную блокировку аккаунта, heartbeat и доступность локальной диагностики. Startup auth failure должен также иметь рабочий control socket: текущего простого возврата ошибки недостаточно.
4. Чтение собранного корпуса через MCP остаётся доступным. Сетевые операции, включая inspect/join, возвращают контрактную ошибку NOT_AUTHENTICATED; новая заявка не отправляется. Чтение сохранённых операций не инициирует мутацию.
5. SIGTERM отменяет ожидание, завершает фоновые задачи, закрывает socket и освобождает lock. При завершении состояние auth_required не заменяется ложным authenticated/connected.

Не приравнивать неизвестные upstream ошибки к auth failure. Сохранить существующую типизированную классификацию и безопасные логи. Сетевые сбои продолжают использовать reconnect; ошибки конфигурации и хранения не превращаются в ожидание авторизации.

Новый вход: остановить LaunchAgent через bootout → выполнить локальный login с телефоном → включить сервис через bootstrap. Ожидающий collector не освобождает lock самопроизвольно. Автоматическое возобновление по изменению файла сессии не требуется.

## Логи и LaunchAgent

Для файловой ротации выбрать небольшую поддерживаемую Go-библиотеку, проверить её актуальные API и закрепить версию. Не писать собственный ротатор без конкретной необходимости. Сохранить slog/JSON и существующую фильтрацию секретов; логировать переход в auth_required один раз, без повторяющихся сообщений ожидания.

Каталог логов — 0700, текущий файл и архивы — 0600. Лимит — текущий файл до 5 МиБ и до трёх архивов. Определить поведение записи, превышающей размер файла, и ошибки открытия/записи sink: диагностика должна быть видна, молчаливый сбой запрещён.

LaunchAgent непосредственно запускает:

```text
/Users/USERNAME/.local/bin/zl-mcp
-config
/Users/USERNAME/.config/zl-mcp/config.toml
collect
```

Сохранить `RunAtLoad=true`, `KeepAlive.SuccessfulExit=false`, `ThrottleInterval=30`, private umask и время для штатного завершения. launchd не различает отдельные неуспешные exit codes этой настройкой; auth_required в сервисном режиме поэтому не завершает процесс. Классификация по тексту stderr не используется. stderr LaunchAgent должен иметь диагностируемое назначение, а не скрывать ошибки запуска без следа.

## Порядок поставки

1. Зафиксировать контракт и реализовать сервисное ожидание и логирование.
2. Пройти автономные проверки, собрать macOS arm64 бинарник без CGO.
3. Подготовить новую версию бинарника, локального конфига и plist; сохранить предыдущие файлы для отката.
4. Штатно выгрузить старый LaunchAgent и проверить освобождение lock. Заменить бинарник атомарно, установить прямой plist и включить сервис.
5. Проверить collector и MCP через установленный бинарник. Проверить автоматическое восстановление после падения.
6. Только после успеха удалить Python runner и обновить инструкции. Системный Python не удалять. Конфигурация MCP остаётся с теми же command/args.

При неуспехе выгрузить новый сервис и восстановить предыдущие бинарник, конфиг и plist. Состояние аккаунта и базу для отката не перезаписывать.

## Критерии приёмки

Тесты используют AAA и fake ports; новый отзыв реального аккаунта для автономных проверок не нужен.

- Startup Restore и listener auth failure в режиме wait сохраняют живой процесс, heartbeat и auth_required без новых сетевых обращений. Проверять отсутствие вызовов наблюдаемыми counters и управляемым временем.
- Сохранённые сообщения и статус доступны через MCP в ожидании; inspect/join отклоняются без upstream мутации. Текущие схемы результатов соблюдены.
- SIGTERM во время ожидания и во время сбора завершает процесс без зависших операций; последующий login/collector получает lock.
- Режим exit сохраняет прежние terminal tests; неправильный конфиг отклоняется.
- Ротация проверена на пересечении границы размера, числе архивов, private permissions и ошибках sink. stdout serve остаётся чистым MCP.
- Проходят go test ./..., go test -race ./..., go vet ./... и сборки macOS arm64/Linux amd64 без CGO.
- Установленный plist проходит plutil -lint; launchctl показывает прямой Go-процесс. Collector не зависит от Python и путей iCloud.
- Реальный MCP status через установленный бинарник подтверждает authenticated=true/connected/last_error=null и сохранность корпуса.
- Принудительное завершение collector приводит к автоматическому запуску нового PID через launchd; после восстановления MCP снова сообщает connected.
- Автозапуск после входа настроен и проверен загрузкой LaunchAgent. Перезагрузку macOS не выполнять без согласования; если её не было, явно записать это в отчёте.
- mac-deployment.md и local-connection.md отражают фактическую установку, управление сервисом, QR-вход и ограничения. Исторические результаты прежних evals не выдаются за новые; если меняются схемы или описания tools/skill, повторить затронутые модельные сценарии.
