# Задача: сбор и обработка всех личных чатов и групп

Статус: реализовано и проверено, установленный сервис мигрирован. Приёмка — [all-conversations-acceptance.md](all-conversations-acceptance.md); исследование и этапы — [conversation-research.md](conversation-research.md).
Дата: 3 октября 2026 года.
Основание: пользователь требует получать и обрабатывать все чаты и группы своего аккаунта.
Это расширение [текущего ТЗ](technical-spec.md): снимает исключение личных сообщений и ограничение сбора выбранными группами. Остальные ограничения, включая отсутствие отправки сообщений и автоматического вступления, сохраняются.

## 1. Результат

Один постоянный Go-сервис собирает входящие и собственные исходящие сообщения всех доступных личных диалогов и групп аккаунта, хранит их в общем корпусе и предоставляет через MCP поиск, контекст, покрытие и подписки. Новые диалоги автоматически включаются в сбор. Для группы требуется фактическое членство; режим «все» не означает вступление в чужие группы.

Одинаковые числовые ID личного диалога и группы не смешивают сообщения. Старый корпус, сессия, подписки и очередь доставки сохраняются при миграции. Архитектура запуска и транспортов остаётся прежней: внутренний collector, HTTP MCP, дополнительный STDIO-мост; инфраструктура callback находится вне сервиса.

«Все» означает все доступные протоколу диалоги аккаунта, включая диалоги с пользователями вне списка друзей, служебные диалоги и новые группы. Недоступные текущему протоколу категории явно отражаются в coverage/capabilities. Полную историю, скрытые и зашифрованные диалоги нельзя объявлять поддержанными без проверки. Скачивание вложений, OCR и обработка аудио остаются вне объёма; сохраняются текст и доступные метаданные вложений.

## 2. Исходное состояние и исследование

| Участок | Исходная реализация | Необходимое изменение |
| --- | --- | --- |
| `internal/zalo/events.go` | Принимает из live/replay только `model.GroupMessage`; запрос replay только для `ThreadTypeGroup`; undo только групповой | Принимать оба типа, запрашивать оба replay, обрабатывать удаление в обоих типах |
| `internal/zalo/adapter.go` | `Convert` принимает `model.GroupMessage` | Общая нормализация сообщения и отдельные преобразования upstream-типов |
| `third_party/zcago/model/message.go` | Уже есть `UserMessage`, `GroupMessage`, `Type()`, `ThreadID()`, `IsSelf()` | Использовать существующие типы; проверить входящее/исходящее направление и нормализацию self UID |
| `third_party/zcago/listener/router.go` | В `handleOldMessages` выбирает группы, если `groupMsgs` непустой; иначе личные сообщения | Обрабатывать оба массива независимо, включая смешанный ответ |
| `third_party/zcago/listener/events/message.go` | Декодер личного сообщения возвращает `nil`, даже если обе попытки разбора не удались | Убрать скрытую потерю и проверить повторное использование объекта |
| Конфигурация и `internal/storage` | Allowlist `collection.group_ids`; таблицы, ключи, FTS, coverage и курсоры используют группу | Общий ключ диалога и политика сбора |
| MCP и `internal/events` | Контракты, ресурсы, payload и подписки используют `group_id` | Контракты диалогов и совместимость групповых клиентов |
| Каталог collector | Обновляет только группы | Каталог диалогов с независимым учётом источника и полноты обнаружения |

У upstream уже есть listener личных сообщений и запросы replay с командами 510/511. Добавлять второй listener, процесс или Python-обвязку не требуется. Список друзей (`GetAllFriends`) не является списком диалогов: нельзя считать всех друзей чатами или исключать сообщения незнакомых пользователей.

Диагностика 3 октября установила, что сообщения со скриншота находятся в личном чате, а действующая подписка относится к группе. Это подтверждённая причина отсутствия именно этих записей. Найденные дефекты декодера и смешанного replay — отдельные проблемы, а не доказанная причина этого случая.

Проверенный групповой replay вернул корректные пустые массивы и с `lastId=null`, и с `lastId="0"`, после получения cipher key. Отдельный `/api/group/history`, описанный в JS-клиенте, вернул API-код 404 при успешном запросе сведений о группе. Поэтому ни пустой replay, ни наличие метода в другом клиенте не доказывают полноту истории или возможность её загрузки для нашего аккаунта. На этом исходном этапе личная история ещё не была проверена; последующие личный replay и восстановление через установленный MCP подтверждены в отчётах исследования и приёмки.

Источники для реализации и сверки протокола:

- Локальный закреплённый `third_party/zcago`, особенно `model/message.go`, `listener/router.go`, `listener/messaging.go` и `api/get_all_friends.go`.
- [Upstream zcago](https://github.com/amrakk/zcago).
- [JS listener и replay](https://github.com/RFS-ADRENO/zca-js/blob/main/src/apis/listen.ts).
- [Отдельная история группы в JS-клиенте](https://github.com/RFS-ADRENO/zca-js/blob/main/src/apis/getGroupChatHistory.ts).

При реализации закрепить версии/commit SHA использованных upstream-источников в отчёте; ссылки на `main` служат навигацией, а не исполняемым контрактом.

## 3. Модель данных и политика сбора

Ввести `ConversationRef { type: "direct" | "group", id: string }`. В публичных JSON использовать `conversation_type` и `conversation_id`; оба поля обязательны при адресации конкретного диалога. ID остаются непрозрачными строками, без преобразования через float64. В Go использовать доменные типы, не экспортировать upstream-структуры.

Ключ сообщения: `(account_key, conversation_type, conversation_id, message_id)`. Этот ключ одинаково применяется к корпусу, идентичностям, событиям, контексту, удалению и дедупликации. Для прямого диалога `conversation_id` — ID собеседника независимо от направления; `sender_id` — фактический автор, включая владельца аккаунта. Для групп ID диалога остаётся ID группы.

Каталог `conversations` содержит тип, ID, доступное имя, источник метаданных, состояние доступности, время первого обнаружения и обновления. Membership и число участников — свойства группы, не фиктивные поля личного чата. Сообщение неизвестного диалога транзакционно создаёт минимальную запись каталога; получение имени не блокирует сохранение текста. Исчезновение из каталога не удаляет корпус.

Предлагаемая конфигурация:

```toml
[collection]
mode = "all" # all | selected
```

`all` собирает оба типа и автоматически включает новые доступные диалоги. `selected` использует список типизированных диалогов (`[[collection.conversations]]` с `type` и `id`). Одновременное задание несовместимых старых/новых параметров возвращает понятную ошибку. Одна политика используется при приёме, поиске, чтении ресурсов и проверке подписок; не создавать разные расходящиеся allowlist в слоях приложения.

Новые примеры установки используют `all`, согласно текущему требованию. Старый конфиг только с `group_ids` сохраняет семантику выбранных групп и получает предупреждение об устаревшем формате. При миграции текущей установки переход на `all` выполняется явно и проверяется; обновление чужой установки само по себе не расширяет её сбор. Retention и приватные права файлов сохраняются.

## 4. Collector, обнаружение и история

1. Нормализовать live и replay обоих типов через общий путь сохранения. Собственные сообщения включены. Обрабатывать оба массива смешанного replay, undo обоих типов и дубликаты live/replay/reconnect.
2. После готовности соединения выполнять replay отдельно для личных диалогов и групп. Проверить необходимую последовательность cipher key/request по живому протоколу; смена момента запроса сама по себе не объявляется исправлением.
3. Использовать API каталога групп и подтверждённый источник списка диалогов, если он доступен. Если полного списка личных чатов нет, обнаруживать их из событий/replay и честно указывать неполноту каталога. Метаданные друзей могут дополнять имена, но не определять допустимость сообщения.
4. Применять ограниченные очереди, backpressure, таймауты и повтор запросов с backoff; не допускать молчаливого overflow. Отделить счётчики входящих кадров, разобранных сообщений, ошибок, исключений политикой и успешных записей, с разбивкой по типу без текста/ID в логах.
5. Не закрывать gaps и не ставить `history_complete=true` лишь по факту WebSocket connection или успешного пустого replay. Сохранять причину и диапазон неопределённого покрытия.

Перед основной реализацией выполнить ограниченную проверку доступной истории обоих типов. Зафиксировать источник списка диалогов, параметры/cursor, формат ответа, лимиты, пагинацию и наличие известных недавних пропущенных сообщений. Использовать существующую сессию без второго одновременного listener; не читать историю из приватной БД нативного Zalo и не импортировать скриншот как сообщение.

Если доступный history API подтверждён, реализовать ограниченную дозагрузку с постоянным checkpoint и общим dedup, в пределах retention и бюджета запросов. Доступный backfill не должен мешать live-сбору. Разделять локальный `received_at`, исходный `sent_at` и источник записи. Новые значения `source`, если понадобятся, сначала включить в исполняемые схемы.

Если источник истории не работает, отдельно документировать точное ограничение и статус восстановления прежних сообщений. Поддержка новых личных сообщений не означает, что вчерашние автоматически появились в корпусе. Отчёт приёмки должен отдельно содержать результат восстановления существующих пропусков; ждать новых вместо этой проверки нельзя. Недоступная история — ограничение этой части, а не повод останавливать реализацию live-сбора.

## 5. MCP: сначала контракты

До изменения реализации подготовить JSON Schema в `docs/contracts`, синхронизировать техническое ТЗ и контрактные тесты. Транспорт MCP и callback-профиль не меняются; не изобретать отдельный HTTP API или tools для подписок.

Целевая поверхность:

- `zalo_list_conversations`: пагинация, необязательный фильтр типа, сведения о полноте каталога и источнике обнаружения.
- `zalo_get_conversation`: адресация типом/ID, метаданные и coverage.
- `zalo_search_conversation_messages`: поиск по всему разрешённому корпусу по умолчанию, фильтр типа или конкретного диалога; каждый hit содержит тип/ID и доступное имя.
- `zalo_get_conversation_message_context`: тип/ID диалога и ID сообщения; контекст никогда не пересекает границу диалога.
- Полный текст через возвращаемый URI с типом диалога и URL-экранированием непрозрачных ID.
- Status/capabilities: режим сбора, число диалогов/сообщений по типам, последнее принятие/сохранение, неполнота каталога и покрытия.

`zalo_list_groups`, `zalo_get_group` и инструменты вступления сохранить как групповые представления/операции. Существующие `zalo_search_messages` и `zalo_get_message_context` оставить групповыми совместимыми фасадами над общим хранилищем. Старые message URI продолжают разрешаться только в группу. Возвращаемые формы legacy-вызовов должны проходить прежние схемы: нельзя просто добавить поля в ответ с `additionalProperties=false`. Новые tools получают отдельные исполняемые схемы; skills используют их для общего поиска. Это добавочное расширение API, без неявной смены семантики старых вызовов.

Курсоры включают тип диалога и параметры запроса; обеспечивают стабильный порядок и не допускают использования с другим фильтром. Учитывать коллизии одинаковых ID между типами. Сохранить лимиты размера ответа, бюджет чтения и понятные ошибки с дальнейшим действием.

## 6. Events и подписки

Сбор всех диалогов и доставка на callback — разные настройки. Все сообщения доступны локальному владельцу через MCP; старые подписки не расширяются на новые личные чаты автоматически.

Новый контракт подписки поддерживает явный scope: один типизированный диалог, все личные, все группы или все доступные диалоги. Режим всех диалогов динамически включает новые, не требует подписки на каждого собеседника. Неограниченную доставку не создавать при старте сервиса: callback и scope по-прежнему выбираются через `events/subscribe`. Формы arguments задаются взаимоисключающим `oneOf`; старый `group_id` остаётся точным групповым scope.

Новый payload содержит тип/ID/доступное имя диалога, ID сообщения, автора, время и текст до 2048 Unicode code points. При обрезке обязательны `text_truncated=true` и URI полного сообщения. Полный текст хранится по прежнему лимиту корпуса. Формат `zalo.message.created` для уже существующих подписок сохранить; новый формат публиковать отдельным событием `zalo.conversation.message.created` со схемой версии 1, отражённым в discovery. Не отправлять несовместимый payload старому receiver.

Сохранить согласованную семантику:

- Только первая запись в сервисе после активации подписки, независимо от `sent_at`; доступные пропущенные записи после reconnect могут дать событие.
- По умолчанию бессрочно до отмены; restart не меняет scope или стартовую границу.
- Дедупликация и идентичности учитывают тип диалога; retention не порождает повторное событие.
- At-least-once доставка с постоянными event ID, очередью, retry и идемпотентностью receiver; порядок внутри подписки сохраняется.
- Undo/retention очищают сохранённые payload по прежним правилам, не оставляя скрытую копию текста.

Для широких scopes проверить рост fanout, квоты очереди, размер индексов и отсутствие блокировки соседних подписок одним медленным receiver. HTTPS verification, подписи и политика адресов сохраняются. Не обещать уведомление конкретного агента без подтверждённой доставки и обработки его receiver.

## 7. Миграция и совместимость

Создать версионированную транзакционную SQLite-миграцию. Сначала проверить частный backup БД и совместимый откат бинарника/БД. Сохранить все существующие сообщения как `group`, исходные seq и timestamps, metadata, collection_started/gaps, identities, подписки, generation/start_seq, fanout checkpoint и pending/sending deliveries. Не генерировать события за перенесённые старые записи.

Обновить уникальные ключи, FTS, индексы, связи и запросы. Старые сериализованные payload очереди остаются в исходной версии до доставки/отмены; адаптация ключей не требует их пересоздания. Проверить целостность и поиск после миграции, повторный запуск миграции и отказ посередине. Смена аккаунта не объединяет его данные с чужими.

Переключение установленной копии выполняется после автономной приёмки, с одним владельцем state и без второго LaunchAgent. Сессию не сбрасывать. Откат включает восстановление совместимого backup БД, а не только старого бинарника поверх новой схемы. Отдельно указать границу backup и судьбу записей, поступивших после неё.

## 8. Проверка и критерии приёмки

Без новых модельных evals. Unit/contract/integration тесты строятся по AAA с синтетическими fixtures. Реальные тексты, имена, ID и credentials не добавлять в репозиторий.

Обязательные сценарии:

1. Входящее и собственное исходящее сообщение прямого диалога дают один и тот же ID диалога и правильного автора; аналогично для групп.
2. Неизвестный собеседник, сообщение не от друга и новая группа включаются в `all`; `selected` сохраняет точную политику.
3. Live, replay личных, replay групп и смешанный replay сохраняют все сообщения без дублей. Некорректный payload даёт безопасную диагностику, а не успешное пустое сообщение.
4. Одинаковые ID диалога/сообщения у разных типов не смешиваются в FTS, контексте, удалении, курсорах или доставке.
5. Поиск по всем диалогам и с фильтром возвращает правильный тип, автора и время; URI полного текста работает для обоих типов. Границы 2048/2049 проверяются на Unicode.
6. Подписки на один диалог и широкие scopes, новый диалог после активации, первая запись старого сообщения после активации, cancellation, restart и retry сохраняют заявленную семантику. Старый callback получает прежний формат.
7. Миграция непустой БД с активной подпиской и очередью сохраняет seq/start_seq/payload и не отправляет историю повторно; legacy tools/URI проходят прежние схемы.
8. Пустой replay не маскирует gap. Overflow/ошибка разбора/недоступность истории видны в безопасной диагностике, `connected` не выдаётся за полноту.
9. Проверки root и вложенного zcago: `test`, `race`, `vet`; сборки без CGO macOS arm64/Linux amd64; контроль нагрузки на синтетическом корпусе со многими диалогами.
10. После реализации — сквозная проверка обоих типов через MCP: приём, поиск, контекст, подписка, доставка, отмена и restart. Отдельно проверить существующие пропущенные сообщения, если API делает их доступными. Исходящие тестовые сообщения не отправлять без соответствующего указания пользователя.

Готовность live-сбора, восстановление доступной истории и доставка Events фиксируются раздельно. Непроверенную категорию нельзя включать в список поддержанных.

## 9. Порядок работ и документация

1. Подтвердить личный replay, источник каталога и доступную историю; записать факты и ограничения.
2. Зафиксировать модель диалога, конфиг, совместимость и версионирование контрактов/Events; добавить исполняемые схемы и тесты.
3. Реализовать общую нормализацию, исправить оба скрытых пути потери в zcago, обновить `third_party/zcago/PATCHES.md`.
