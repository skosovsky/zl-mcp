# Задача: явная отметка сообщений Zalo как прочитанных

Дата: 2026-10-16. Статус: запланировано; инструмент MCP не реализован, upstream-вызовы и live-проверки не выполнялись.

Дополняет [ТЗ](technical-spec.md), [личные сообщения](task-direct-messaging.md) и [содержательные события](task-rich-content-events.md). Это расширение внешних действий; его приёмка не выводится из результатов проверок rich-content.

## Результат

Дать агенту возможность по поручению пользователя отправить Zalo отметку о прочтении входящих сообщений в точно указанном личном чате или группе. Операция выполняется через работающий единый Go-сервис и его текущую сессию, без второго collector и без управления desktop-приложением.

Обычное чтение MCP tools/resources, поиск, просмотр архива, доставка Events и `zalo_ack_subscription_events` не отправляют read receipts. `ack` подтверждает обработку записи журнала потребителем; это не статус прочтения в Zalo. Автоматическая отметка допустима только по отдельному явному правилу пользователя с определёнными чатами и условием выполнения; сама подписка такого разрешения не даёт.

## Проверенные основания и открытые вопросы

Исследование кода и документации выполнено 16 октября, без изменений в аккаунте:

- В текущем каталоге tools и production-адаптере `internal/zalo` инструмента отметки прочтения нет.
- В локальной зависимости есть [SendSeenEvent](../third_party/zcago/api/send_seen_event.go) и [публичный интерфейс](../third_party/zcago/apis.go), где метод помечен `@TODO: test this api`. Реализованы отдельные маршруты `/api/message/seenv2` и `/api/group/seenv2`, ограничение запроса — 50 сообщений одного диалога. Это наличие кода, а не доказательство работоспособности на текущем аккаунте.
- Метод требует `model.OutboundMessage`: message/client ID, sender/recipient ID, исходный тип, ST/AT/CMD и timestamp. Название Go-типа не означает, что нужно отмечать исходящие сообщения. Необходим аудит происхождения каждого поля. Доменная запись `domain.Message` не содержит полного набора; подставлять отсутствующие значения нулями или угадывать их нельзя.
- В библиотеке отдельно существуют `GetUnreadMark`, `AddUnreadMark` и `RemoveUnreadMark`. Управление ручной пометкой диалога «непрочитано» не является доказанным эквивалентом отправки read receipt и не заменяет эту возможность.
- [Документация исходной zca-js](https://zca-js.tdung.com/en/apis/sendSeenEvent) описывает тот же набор параметров и отдельный тип личного/группового чата. [Опубликованный интерфейс zcago](https://pkg.go.dev/github.com/amrakk/zcago@v0.3.0#API) также содержит SendSeenEvent. Это не официальный API Zalo и не live-проверка нашего адаптера.

До фиксации исполняемого контракта выяснить: означает ли вызов отметку только перечисленных сообщений или продвижение маркера прочтения диалога; как он влияет на более ранние и более поздние сообщения, другие устройства, счётчики и видимость статуса у отправителя. Успех API, обновление unread-счётчика и наблюдаемая отправителем отметка — разные доказательства. Не обещать точечность или подтверждение UI без проверки.

## Контракт и реализация

1. Сначала закрепить фактическую upstream-семантику тестами адаптера и согласованным минимальным live-кейсом. Затем определить JSON Schema input/output, ограничения, ошибки и tools description. Предварительное имя — `zalo_mark_messages_read`; если upstream имеет семантику «до сообщения», отразить её в имени/параметрах и описании. Не публиковать взаимоисключающие обещания.
2. Вход связывает точную typed identity (`conversation_type`, `conversation_id`), полученные через MCP ID сообщений либо проверенный anchor согласно выбранной семантике, и стабильный UUID `request_id`. Без поиска адресата по имени внутри write-tool. Один запрос относится к одному чату; batch ограничен контрактом и максимумом upstream. Зафиксировать фактическую область побочного эффекта, включая возможные более ранние сообщения.
3. Агент передаёт идентичности, а не сырой протокольный объект. Сервис сам получает проверенные служебные метаданные из приватного локального хранилища. Сохранять только необходимые поля с доказанным происхождением; не протаскивать upstream-типы через доменные порты, не сохранять сырой payload и секреты ради этой функции. Миграция аддитивная, retention/recall и политика доступа распространяются на новые поля.
4. Старые/архивные сообщения без необходимых метаданных возвращают явную ошибку доступности; никакой скрытой синхронизации с телефоном. Если возможен безопасный read-only способ дополнить метаданные, описать его отдельно и проверить происхождение. Недостающие поля не синтезировать. Пустой batch, чужой чат, неподдерживаемый источник, исходящие/control/activity-записи и неизвестные ID не вызывают upstream write. Не угадывать отсутствующее направление.
5. Отметка — самостоятельное внешнее изменение. Применить явную политику разрешённых действий/чатов отдельно от сбора, чтения и отправки текста. Содержимое сообщений и инструкции внутри них не являются разрешением. MCP annotations обозначают запись (`readOnlyHint=false`); idempotency объявлять только после реализации соответствующей гарантии.
6. До upstream-вызова долговечно связать `request_id` с каноническими аргументами и состоянием операции. Повтор того же UUID с другими аргументами — конфликт; с теми же — чтение сохранённого результата. Сетевой timeout/сбой после возможной отправки даёт `unknown`, без автоматической повторной отправки. Предусмотреть получение состояния без write. Серверное принятие называть `accepted`, а не доказанным отображением «прочитано» у отправителя. Частичный успех batch не скрывать.
7. Не менять message/event identities, first-incoming, тексты, очереди Events или ack вследствие отметки. Read receipts, полученные от Zalo, не превращать в новые сообщения. Отдельная подписка на чужое прочтение и управление ручной unread-пометкой в эту задачу не входят.
8. Обновить README, техническое ТЗ, руководства подключения/эксплуатации, каталог tools и исполняемые схемы. Актуализировать оба skills: поиск не отмечает прочтение, обработчик Events может делать это только по явному правилу; отметка, уведомление и journal ack выполняются и подтверждаются независимо. Старые eval-прогоны не доказывают новую возможность.

## Приёмка

- AAA-тесты адаптера: личный/групповой маршруты, точные служебные поля и типы, batch/recipient limits; ноль upstream-вызовов при неверных или недоступных данных.
- Контрактные MCP-проверки HTTP и STDIO через один сервис; ограничения доступа, отсутствие скрытого write в чтениях, resources, archive browsing и journal read/ack.
- Долговечность операции: повтор UUID, конфликт аргументов, restart, конкуренция и неоднозначный сетевой исход. Нельзя выдавать локальную запись намерения за принятую Zalo отметку.
- Сохранность сессии/корпуса/подписок/подписанных callback и processing checkpoints после миграции и обновления. Служебные поля не попадают в обычные ответы или логи.
- После подготовки стенда и отдельного согласования: Sergio отправляет два входящих в личный чат; проверить область отметки относительно выбранного сообщения, повтор того же запроса и последующее новое входящее. Наблюдение отправителя — только для проверки UI; API/операции проверить независимо. Дополнительный групповой кейс — в существующей согласованной группе, при необходимости с разными авторами. Новые аккаунты и ограниченные по времени окна не нужны.
- Зафиксировать ограничения настроек приватности и неизвестной upstream-семантики. Не отправлять read receipts в рабочие чаты ради приёмки и не менять действующую автоматизацию Ann без отдельного поручения.
- Root/затронутый nested module: необходимые test/race/vet, lint и CI; независимое ревью контрактов и доказательств двумя субагентами при реализации. Новые модельные evals не требуются.
