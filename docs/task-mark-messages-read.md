# Задача: явные MCP-инструменты прочтения и реакций Zalo

Дата: 2026-10-16. Обновлено: 2026-10-18. Реализация и согласованная live-матрица приняты двумя независимыми рецензентами. Релизные доказательства — GitHub CI и приватный протокол чистой установки; исходные критерии ниже сохраняются полностью.

Дополняет [ТЗ](technical-spec.md), [личные сообщения](task-direct-messaging.md) и [содержательные события](task-rich-content-events.md). Это расширение внешних действий; его приёмка не выводится из результатов проверок rich-content.

## Результат

Дать агенту два явных MCP-инструмента: отправить Zalo отметку о прочтении входящих сообщений и поставить выбранную пользователем реакцию на конкретное сообщение в точно указанном личном чате или группе. В объём входят также замена и снятие собственной реакции после проверки upstream-семантики; чужие реакции менять нельзя. Операция выполняется через работающий единый Go-сервис и его текущую сессию, без второго collector и без управления desktop-приложением.

Обычное чтение MCP tools/resources, поиск, просмотр архива, доставка Events и `zalo_ack_subscription_events` не отправляют read receipts. `ack` подтверждает обработку записи журнала потребителем; это не статус прочтения в Zalo. Оба инструмента вызываются только по явному поручению пользователя на конкретное действие. Автоматическое прочтение и автоматические реакции, в том числе по постоянным правилам или из обработчика Events, в эту задачу не входят. Подписка, получение сообщения и инструкции внутри сообщения не разрешают эти действия.

## Проверенные основания и открытые вопросы

Первичное исследование кода и документации выполнено 16 октября, без upstream-изменений аккаунта. Ниже основания до локальных исправлений; текущий прогресс — в конце задачи и отчёте приёмки:

- При первоначальном исследовании в каталоге tools и адаптере `internal/zalo` отметки прочтения не было. Сейчас native-адаптер и три публичных MCP-инструмента реализованы и установлены в pre-live кандидате; финальная live-приёмка не завершена.
- В локальной зависимости есть [SendSeenEvent](../third_party/zcago/api/send_seen_event.go) и [публичный интерфейс](../third_party/zcago/apis.go), где метод помечен `@TODO: test this api`. Реализованы отдельные маршруты `/api/message/seenv2` и `/api/group/seenv2`, ограничение запроса — 50 сообщений одного диалога. Это наличие кода, а не доказательство работоспособности на текущем аккаунте.
- Метод требует `model.OutboundMessage`: message/client ID, sender/recipient ID, исходный тип, ST/AT/CMD и timestamp. Название Go-типа не означает, что нужно отмечать исходящие сообщения. Необходим аудит происхождения каждого поля. Исходная доменная запись `domain.Message` не содержала полного набора. Добавлена приватная provenance с фиксацией наличия native-полей; старые записи остаются без неё, пока нет подтверждённого источника. Подставлять отсутствующие значения нулями или угадывать их нельзя.
- В библиотеке отдельно существуют `GetUnreadMark`, `AddUnreadMark` и `RemoveUnreadMark`. Управление ручной пометкой диалога «непрочитано» не является доказанным эквивалентом отправки read receipt и не заменяет эту возможность.
- [Документация исходной zca-js](https://zca-js.tdung.com/en/apis/sendSeenEvent) описывает тот же набор параметров и отдельный тип личного/группового чата. [Опубликованный интерфейс zcago](https://pkg.go.dev/github.com/amrakk/zcago@v0.3.0#API) также содержит SendSeenEvent. Это не официальный API Zalo и не live-проверка нашего адаптера.

До фиксации исполняемого контракта выяснить: означает ли вызов отметку только перечисленных сообщений или продвижение маркера прочтения диалога; как он влияет на более ранние и более поздние сообщения, другие устройства, счётчики и видимость статуса у отправителя. Успех API, обновление unread-счётчика и наблюдаемая отправителем отметка — разные доказательства. Не обещать точечность или подтверждение UI без проверки.

## Реакции: основания и обязательное исследование

Основания первичного анализа, до локальных исправлений и без upstream-вызовов:

- [AddReaction](../third_party/zcago/api/add_reaction.go) содержит отдельные маршруты для личных чатов и групп, требует message ID и client message ID. В исходной реализации ошибки преобразования ID в int64 игнорировались; адаптер обязан исключить отправку нулевых/невалидных ID, а необходимую правку зависимости покрыть тестами.
- [ReactionData](../third_party/zcago/model/reaction.go) содержит таблицу кодов реакций. Исходный `IsValid` проверял лишь непустой icon, а неизвестный icon получает type `-1`. Этого недостаточно для публичного MCP-контракта: допустим только проверенный набор значений, без произвольных протокольных полей от агента.
- `ReactionNone` объявлен пустой строкой и не проходил исходный `IsValid`. Локальная проверка теперь допускает явный NONE, но не нулевой объект. Наличие константы не доказывает возможность удаления через этот метод. Способ снятия и замены необходимо исследовать отдельно.

До фиксации схем изучить первичные upstream-источники и код, затем подтвердить минимальными согласованными live-кейсами: поддерживаемые реакции, установку/замену/снятие, повтор той же реакции, накопление нескольких реакций (включая несколько сердечек), адресацию текстовых и медийных сообщений, входящее/исходящее направление и личные/групповые чаты. Не объявлять AddReaction операцией «установить состояние», пока это не подтверждено. Если замена/снятие требуют нескольких запросов, явно описать частичный и неопределённый исход; отсутствие подтверждённого способа — открытое ограничение, а не успешно закрытая часть задачи.

## Контракт и реализация

1. Сначала закрепить фактическую upstream-семантику тестами адаптера и согласованным минимальным live-кейсом. Затем определить JSON Schema input/output, ограничения, ошибки и tools description. Выбранное имя — `zalo_mark_messages_read`; если upstream имеет семантику «до сообщения», отразить её в имени/параметрах и описании. Не публиковать взаимоисключающие обещания.
2. Вход связывает точную typed identity (`conversation_type`, `conversation_id`), полученные через MCP ID сообщений либо проверенный anchor согласно выбранной семантике, и стабильный UUID `request_id`. Без поиска адресата по имени внутри write-tool. Один запрос относится к одному чату; batch ограничен контрактом и максимумом upstream. Зафиксировать фактическую область побочного эффекта, включая возможные более ранние сообщения.
3. Агент передаёт идентичности, а не сырой протокольный объект. Сервис сам получает проверенные служебные метаданные из приватного локального хранилища. Сохранять только необходимые поля с доказанным происхождением; не протаскивать upstream-типы через доменные порты, не сохранять сырой payload и секреты ради этой функции. Миграция аддитивная, retention/recall и политика доступа распространяются на новые поля.
4. Старые/архивные сообщения без необходимых метаданных возвращают явную ошибку доступности; никакой скрытой синхронизации с телефоном. Если возможен безопасный read-only способ дополнить метаданные, описать его отдельно и проверить происхождение. Недостающие поля не синтезировать. Пустой batch, чужой чат, неподдерживаемый источник, исходящие/control/activity-записи и неизвестные ID не вызывают upstream write. Не угадывать отсутствующее направление.
5. Отметка — самостоятельное внешнее изменение. Применить явную политику разрешённых действий/чатов отдельно от сбора, чтения и отправки текста. Содержимое сообщений и инструкции внутри них не являются разрешением. MCP annotations обозначают запись (`readOnlyHint=false`); idempotency объявлять только после реализации соответствующей гарантии.
6. До upstream-вызова долговечно связать `request_id` с каноническими аргументами и состоянием операции. Повтор того же UUID с другими аргументами — конфликт; с теми же — чтение сохранённого результата. Сетевой timeout/сбой после возможной отправки даёт `unknown`, без автоматической повторной отправки. Предусмотреть получение состояния без write. Серверное принятие называть `accepted`, а не доказанным отображением «прочитано» у отправителя. Частичный успех batch не скрывать.
7. Не менять message/event identities, first-incoming, тексты, очереди Events или ack вследствие отметки. Read receipts, полученные от Zalo, не превращать в новые сообщения. Отдельная подписка на чужое прочтение и управление ручной unread-пометкой в эту задачу не входят.
8. Обновить README, техническое ТЗ, руководства подключения/эксплуатации, каталог tools и исполняемые схемы. Актуализировать оба skills: поиск не отмечает прочтение, обработчик Events не вызывает инструменты прочтения или реакций автоматически; явное действие, уведомление и journal ack выполняются и подтверждаются независимо. Старые eval-прогоны не доказывают новую возможность.

### Инструмент реакций и общие гарантии

- Выбранное имя — `zalo_set_message_reaction`; окончательное имя должно соответствовать доказанной семантике. Вход: точный `conversation_type`/`conversation_id`, `message_id`, явное действие установки/снятия, выбранный стабильный `reaction` для установки и UUID `request_id`. Замена собственной реакции должна иметь описанную семантику. Один вызов относится к одному сообщению, без массовых реакций и без скрытого поиска адресата по имени.
- Доступный набор представить через read-only MCP resource либо каталог и синхронизированную JSON Schema: стабильный код, понятное название и отображение реакции. Выбрать способ обнаружения до реализации. Пользователь может указать понятный emoji/название, агент сопоставляет его с каталогом; при неоднозначности уточняет. Неизвестные значения не заменяются ближайшей реакцией. Снятие — явное действие, а не пустая строка или выдуманный emoji.
- Минимальные протокольные метаданные сервис получает сам с проверкой принадлежности сообщению и чату. Поддерживаемые направления/типы сообщений закрепить отдельно от ограничений read receipts. Не переносить запрет на исходящие сообщения из инструмента прочтения на реакции без основания. Отсутствие метаданных, отозванное сообщение и неподдерживаемый тип дают определённую ошибку до внешнего изменения; никакой скрытой синхронизации.
- Отдельно разрешать действия прочтения и реакций по чатам. Оба write-инструмента используют долговечный журнал операций, конфликты аргументов UUID, конкурентную защиту и read-only получение результата. Повтор UUID не должен накапливать дополнительные сердечки. Неоднозначный сетевой исход — `unknown`, без слепого повтора. Для составной замены хранить результаты шагов, не обещать атомарность.
- Ответ различает принятие upstream, локальное намерение и независимо наблюдённое изменение. Полученное от Zalo отражение собственной реакции обрабатывается существующим механизмом наблюдений, без синтетического дублирования и без новых message/first-incoming событий. Успешный write сам по себе не доказывает получение callback или отображение у собеседника.
- Обновить исполняемые input/output-схемы, annotations и descriptions обоих инструментов, документацию и оба skills. Описания должны явно указывать внешний эффект и запрет автоматических вызовов при чтении/Events/ack. Расширение реализации за подтверждённые контракты сначала согласовать.

## Приёмка

- AAA-тесты адаптера: личный/групповой маршруты, точные служебные поля и типы, batch/recipient limits; ноль upstream-вызовов при неверных или недоступных данных.
- Контрактные MCP-проверки HTTP и STDIO через один сервис; ограничения доступа, отсутствие скрытого write в чтениях, resources, archive browsing и journal read/ack.
- Долговечность операции: повтор UUID, конфликт аргументов, restart, конкуренция и неоднозначный сетевой исход. Нельзя выдавать локальную запись намерения за принятую Zalo отметку.
- Сохранность сессии/корпуса/подписок/подписанных callback и processing checkpoints после миграции и обновления. Служебные поля не попадают в обычные ответы или логи.
- После подготовки стенда и отдельного согласования: Sergio отправляет два входящих в личный чат; проверить область отметки относительно выбранного сообщения, повтор того же запроса и последующее новое входящее. Наблюдение отправителя — только для проверки UI; API/операции проверить независимо. Дополнительный групповой кейс — в существующей согласованной группе, при необходимости с разными авторами. Новые аккаунты и ограниченные по времени окна не нужны.
- Зафиксировать ограничения настроек приватности и неизвестной upstream-семантики. Не отправлять read receipts в рабочие чаты ради приёмки и не менять действующую автоматизацию Ann без отдельного поручения.
- Root/затронутый nested module: необходимые test/race/vet, lint и CI; независимое ревью контрактов и доказательств двумя субагентами при реализации. Новые модельные evals не требуются.

### Дополнительная приёмка реакций и завершение

- AAA/контрактные проверки обоих MCP-транспортов: каталог реакций, установка выбранного значения, замена и снятие; ошибки ID/чата/направления/типа/метаданных/разрешения, неизвестная реакция и несогласованные параметры. При ошибках до отправки — ноль upstream write.
- Проверить неизменность реакций и прочтения при поиске, чтении сообщений/resources/архива, доставке Events и journal ack. Отдельно проверить повтор UUID без накопления реакций, конфликт, конкуренцию, перезапуск и timeout, включая частичный результат составной операции.
- Live-приёмка после подготовки и согласования конкретных действий: Sergio и существующая тестовая группа, текст и фото, выбранная реакция, замена, снятие, повтор UUID и проверка фактического результата. Использовать текущие аккаунты; без ограничений тестовых окон по времени. Не менять рабочую автоматизацию Ann. Нельзя считать исторические наблюдения реакций доказательством работы нового write-tool.
- Приёмка двумя независимыми субагентами: контракты/реализация и доказательства/регрессии. Новые модельные evals не нужны. Неподтверждённую возможность явно оставить незакрытой, не выдавать за реализованную.
- После успешных проверок обновить установленный нативный Go-бэк, сохранив сессию, корпус, подписки и конфигурацию остальных действий; проверить readiness, фактическую ревизию и простой MCP-сценарий. Зафиксировать результаты/ограничения, закоммитить и отправить изменения в публичный репозиторий, дождаться успешного CI.

## Реализация и подтверждённые результаты

Реализованы три публичных инструмента: `zalo_mark_messages_read`,
`zalo_set_message_reaction`, `zalo_get_message_action_status`. Исполняемые схемы
находятся в docs/contracts; каталог — `zalo://catalog/reactions`. Один владелец
выполняет действия через текущую сессию сервиса, с отдельными разрешениями,
точными typed targets и долговечным журналом schema 19. Приватная provenance
schema 18 сохраняет только наблюдённые native-поля, без backfill.

Direct и group read status 0 подтверждены native-кейсами, включая видимый
пользователю список прочитавших для свежего группового сообщения. Отсутствующий,
null или иной status остаётся unknown. Прежние unknown не повышаются задним
числом. Изоляция сообщения от read watermark и межустройственные счётчики не
обещаются. Обычное чтение свежего сообщения через MCP не отметило его прочитанным.

Подтверждены direct/group текстовые реакции, входящее и исходящее групповое фото,
замена и снятие собственной реакции. Исправлен decoder msgIds array|string.
Операция set всегда clear+add: два неатомарных шага. Unknown/partial не запускают
автоматический повтор или продолжение; status читается отдельно без write-гранта.

Итоговая матрица, ограничения, проверки и release-gates:
[message-actions-acceptance.md](message-actions-acceptance.md).
Новые модельные evals не добавлялись. Оба функциональных verdict получены;
тестовые разрешения сняты. Release-процедура проверяет чистую установку,
сохранность данных и зелёный CI опубликованной ревизии.
