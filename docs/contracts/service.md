# Основной режим service, версия 1

Расширение личной отправки сохраняет этот lifecycle: Sender использует восстановленную
сессию внутреннего collector. allow_send по умолчанию false; send_recipient_ids отдельно
ограничивает адресатов. При старте под account lock прерванные sending переходят в
unknown до открытия MCP endpoint. HTTP и STDIO предоставляют tools отправки/статуса,
Events остаются HTTP. Миграции 5/6 добавляют журнал без текста, quote metadata,
постоянные признаки входящих и фильтры подписок. Не создавать вторую сессию или процесс.
Контракт: [direct-messaging.md](direct-messaging.md).

Отправка ограничена 30 секундами upstream-вызова и 3 секундами независимой записи
результата; MCP call budget — 35 секунд. STDIO HTTP-мост ждёт до 40 секунд, HTTP
write timeout сервиса — 45 секунд. Контекст HTTP-запросов наследует lifecycle
сервиса: остановка отменяет upstream-вызов, а запись неоднозначного результата
завершается до закрытия SQLite. Ошибка транспорта не разрешает повтор с новым UUID.

Команда: `zl-mcp -config CONFIG service`, без позиционных аргументов.
Процесс владеет account lock, SQLite, MCP listener, внутренним collector и delivery worker. Второй service или login с тем же state_dir отклоняется до восстановления сессии.

## Конфигурация транспорта

В TOML добавляется таблица `[mcp]`: `listen` (по умолчанию `127.0.0.1:18765`) и `token_file` (по умолчанию `state_dir/mcp-token`). Нормализованная таблица проверяется по `service_config.input.json`. Listen допускает только буквальные loopback-адреса IPv4/IPv6 и порт 1–65535; DNS-имена и bind на внешние интерфейсы запрещены. Endpoint — `/mcp`. Публикация через proxy относится к инфраструктуре.

Token file — абсолютный путь после разрешения относительно каталога config, обычный приватный файл. Если отсутствует, service создаёт 32 случайных байта в hex-представлении (64 ASCII-символа), mode 0600, без перезаписи существующего файла. Существующее значение после удаления внешних пробелов должно содержать не менее 32 и не более 4096 ASCII-символов без пробелов и управляющих символов. Токен никогда не выводится в логи или MCP-ответы. Клиент передаёт `Authorization: Bearer TOKEN`.

## Lifecycle

HTTP и delivery worker запускаются независимо от успешности Zalo Restore. Известная потеря авторизации переводит collector в `auth_required`, сохраняет gap и прекращает сетевые операции Zalo до остановки сервиса и интерактивного login. Корпус и сохранённые результаты операций остаются доступны. Неизвестная ошибка Restore повторяется с ограниченной задержкой, без QR.

Collector не открывает сокет. Service может предоставить private Unix IPC исключительно доверенным CLI-операциям preview/approve; этот интерфейс не принимает MCP membership-вызовы. Основной MCP вызывает доменный порт внутри процесса.

При SIGTERM общий контекст отменяется, HTTP закрывается с deadline, collector и delivery worker завершаются до закрытия SQLite и освобождения lock. Ошибка обязательного компонента останавливает процесс для восстановления launchd. Auth-required не является причиной выхода или повторной авторизации.

## Файловые логи

Таблица `[logging]` сохраняет `level` и добавляет `file`, `max_size_mb` (по умолчанию 5) и `max_backups` (по умолчанию 3). Путь по умолчанию — `~/Library/Logs/zl-mcp/service.log` после раскрытия home в конфигурационном загрузчике, относительный путь разрешается относительно config. Нормализованные поля проверяются по `service_logging.input.json`. Файловый sink используется только основным service и открывается после захвата account lock. Остальные CLI-режимы пишут в stderr.

Go slog пишет JSON через закреплённый lumberjack v2.2.1; один процесс владеет файлом. Каталог 0700, файл и архивы 0600. Размер задаётся в МиБ; cleanup архивов асинхронный, после завершения cleanup остаются не более max_backups. Архивы не сжимаются.

Ошибка открытия sink прерывает запуск и остаётся в stderr. Ошибка записи или запись больше максимального размера файла выдаёт короткую JSON-диагностику в stderr и завершает service с ошибкой для восстановления launchd. Исходная запись при сбое не копируется в stderr: это предотвращает неограниченное дублирование больших записей. Ошибка не игнорируется slog. Секреты и тела сообщений не логируются.

## STDIO bridge

`zl-mcp -config CONFIG serve` — краткоживущий клиентский мост к работающему service. Он читает существующий token_file и подключается к loopback MCP endpoint; не создаёт SQLite, account lock, Zalo client или listener. Проксирует tools и resources, сохраняя их схемы, описания и ответы. Отсутствие service или токена приводит к явной ошибке запуска. Стандартные Events вызываются непосредственно через основной HTTP transport; bridge не объявляет Events capability. stdout содержит только MCP, диагностика идёт в stderr. Это дополнительный процесс на время STDIO-подключения, а не второй постоянный сервис.

После успешной миграции основной CLI больше не поддерживает `collect`. Единственный постоянный режим — `service`; `serve` остаётся клиентским мостом. Для запуска старой установки при откате используется сохранённый прежний бинарник.

## Ранние ошибки запуска

Для service CLI ошибки, возникшие до открытия основного sink, записываются в отдельный приватный `~/Library/Logs/zl-mcp/startup.log` через тот же Go-ротатор: 5 МиБ, три архива. Запись содержит время, PID, безопасную категорию и указание запустить команду интерактивно для подробностей; исходное сообщение ошибки не публикуется в файловой диагностике. Записи сериализованы отдельным file lock с ограниченным ожиданием. Файл и архивы 0600, каталог 0700. В интерактивном терминале полная ошибка также выводится в stderr. При недоступном startup sink короткая безопасная диагностика остаётся в stderr; выход всегда неуспешный.

LaunchAgent направляет stderr в `startup.log`. Штатные ошибки CLI service передаются Go-ротатору; FlagSet не дублирует их в файл до обработки. Сообщения OS loader и аварийные runtime trace до управления приложением остаются внешней диагностикой launchd и не являются JSON-логами приложения.

При известном auth failure внутренний session guard помечает upstream недоступным и отменяет общий сетевой контекст уже принятых Zalo-операций. Последующие membership-вызовы отклоняются с NOT_AUTHENTICATED до обращения к адаптеру, включая короткий промежуток между ошибкой listener и переходом service в ожидание. Чтение сохранённого результата операции не требует upstream и остаётся доступным. Сетевые ошибки не включают этот guard.

Владелец service фиксирует restart gap от предыдущего heartbeat до первой записи нового состояния, затем сообщает authenticated=false/reconnecting во время Restore. Независимый heartbeat раз в 10 секунд обновляет только временную метку; он не заменяет состояние listener и не сообщает ложный connected. Heartbeat действует во время Restore, backoff и auth_required, завершается до закрытия SQLite; ошибка записи завершает сервис с диагностируемой ошибкой. Повторные BeginGap сохраняют начало открытого разрыва.

## Общая политика диалогов

Service открывает SQLite с единой typed политикой из `[collection]`: `mode = "all"` либо `mode = "selected"` с `conversations = [{type, id}]`. Старый group_ids без mode сохраняет значение; смешение форм отклоняется. Нормализованный контракт — collection_policy.input.json. Политика одинакова для collector, read tools и delivery claim.

Collector слушает direct/group live и replay, включая self-сообщения, и обнаруживает диалоги при записи. Connected не закрывает gaps: полнота replay неизвестна. Нормализация личного чата сохраняет ID собеседника, автор независим. Широкий сбор не создаёт и не расширяет подписки. Общие инструменты и zalo://collection доступны также через STDIO bridge; все Events профили вызываются непосредственно через HTTP.

Миграция SQLite сохраняет seq, identities, FTS, gaps, подписки/границы/поколения и payload очереди. Один владелец state по-прежнему обязателен. Вернуть прежний бинарник после миграции можно только с совместимой резервной копией state.

## Sending permissions

The executable [permissions schema](service_permissions.input.json) validates
`allow_join`, `allow_send` and `send_recipient_ids` after TOML defaults are applied.
Recipient IDs are unique opaque strings of 1–256 Unicode characters. An omitted
or empty recipient list imposes no recipient restriction when `allow_send=true`;
`allow_send=false` still disables every send. Configuring a recipient list while
sending is disabled is allowed. These permissions do not expand collection policy.
