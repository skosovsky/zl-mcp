# Rich content Events: implementation contract

Status: native candidate installed; live/final acceptance pending. Existing legacy and v2
wire payloads remain unchanged. New schemas are embedded locally; a schema's
presence alone is not proof that a production client has discovered it.

## Message profile v3

`zalo.conversation.message.created.v3` reuses the v2 typed conversation selectors,
direction filters and first-incoming policy. It adds required `data.content`
([schema](message_content.output.json)), and sets `schema_version=3`. Required `content_resource_uri` points to bounded local JSON metadata (`.../messages/{message_id}/content`), never media bytes. It applies the same current collection policy, recall and TTL visibility as the message. Existing text resources keep their representation unchanged.
`eventId` comes from the same durable message event as other profiles, not from a
new random ID per encoder/retry. Cross-profile migration must still reconcile
source conversation/message identity rather than assume all future event
families share this ID scheme.

Content summary is generated by the service. `text` is the semantic author-text projection for newly classified content;
old records explicitly declare `text_role=legacy_projection`. Attachment titles
are excluded from v3 text and preserved only as metadata labels, except the
controlled incoming direct single-photo caption shape described below. An attachment label
is neither a proven caption nor a filename. `bytes_available=false` is explicit:
no media download/resource is promised. URLs, arbitrary native params and private
transport metadata never enter the content model. Every content/element field is
bounded. Unknown old projections use reason `legacy_projection`; no historical
call/photo identity can be reconstructed from an empty string.

Newly encoded v3 envelopes include `content_truncated`. To keep every retained
message event recoverable through the journal, the serialized envelope is capped
at 26 KiB, leaving space within the 28 KiB journal page for receipt/entry metadata.
The complete schema-valid content is validated before projection. If necessary,
only trailing content elements are omitted from a copy until the envelope fits;
`content_truncated=true` explicitly directs the consumer to `content_resource_uri`
for all elements. Stored content and the full metadata resource are unchanged.
Text uses its independent 2048-code-point truncation/resource contract. Callback
and journal expose the same projected envelope/content; journal JSON formatting
need not be byte-identical. Stored callback/retry/signature bytes remain immutable. Earlier signed v3 envelopes
may omit `content_truncated`; absence means false and does not rewrite those bytes.
Strict v3 clients must refresh discovery/output schemas before accepting newly
encoded envelopes with this optional field; v2 consumers are unchanged.

Typed message context and browse responses may contain optional `content`.
Legacy group response JSON stays unchanged. Older rows without a retained content
projection keep that field absent on reads; v3 envelopes use explicit legacy
unsupported content. Existing signed v2 delivery bytes must never be regenerated
to add content. This schema extension is additive for typed reads; strict clients
must refresh the tool schema before using the optional field.

### Controlled direct-media refinements

The native test batch on 2026-10-16 established an incoming direct photo whose
attachment `title` exactly matched the instructed synthetic caption, paired with
the previous title-less photo. Caption attribution is restricted to `chat.photo`
with a nonempty valid UTF-8 title, empty action/type, zero child count, no quote,
and a bounded JSON-object params containing numeric width/height and no
`groupLayoutId`, `isGroupLayout`, `idInGroup` or `totalItemInGroup` key (including
present zero/empty values). For this shape only, title supplies author text via
the existing truncation/full-text-resource path; the duplicated metadata label
is omitted. Group, outgoing, quoted, album and incomplete shapes retain their
metadata-only projection. Forwarded-photo semantics are not separately proved.

The same batch established incoming direct `chat.recommended` with exact
attachment action `recommened.link` and empty attachment type. This discriminator
refines the kind to link; title remains a metadata label, never author text, and
native URLs/params remain private. Other recommendation actions remain unknown.
Both refinements run after direction resolution in the shared live/replay and
preload conversion routes. Historical imports remain silent.

The controlled file's title also exactly matched its instructed synthetic
filename. Incoming direct `share.file` with empty action/type and a nonempty
valid UTF-8 title therefore additionally exposes bounded `elements[].file_name`
(at most 256 Unicode characters). The label remains metadata and text_role stays
none. Filename is a display value, never a filesystem path or action authority.
No size/duration/dimension units are inferred from numeric parameter names.

Native evidence and offline evidence are distinct: the received batch proves
the observed shapes; additional quote/album-negative guard fixtures are
synthetic. Already persisted corpus and signed callback/journal bodies are not
rewritten when adding these refinements. In particular, the seven deliveries
from the first batch retain their original projection and are acknowledged only
after exact signed-body/journal verification.

The local decoder previously required nonempty attachment title, and interpreted
JSON null as empty text. Its new union handling clears stale arms, distinguishes
null and preserves title-less structured objects. Unknown fields remain native
objects locally until the normalizer projects an explicit bounded model.

## Control records

A native `chat.undo` or object with the `deleteMsg` marker follows the control
classification established by the local SDK and the pinned upstream listener.
Arrays are an SDK-shape quarantine, not proven deletion semantics from the
pinned JS reference. Nonempty arrays matching that SDK model require explicit
`actionType` and a positive `globalDelMsgId` on every element. Generic arrays,
empty arrays and `[{}]` remain unsupported content, not fabricated controls.
Recognized control-shaped records bypass message persistence and novelty in
live/replay, group history and preload; safe logs identify only their source and
classification. Their numeric action values are not mapped to target mutations
without evidence. Existing typed live Undo handling remains separate and applies
the established recall callback. No claim is made that skipping a historical
control reconstructs deleted history or proves complete control replay.

## Activity families

The native call classifier recognizes only direct `chat.recommended` records
with attachment action exactly `recommened.misscall` or `recommened.calltime`,
independently matched in native records after user-confirmed calls. The parameter
object is bounded to 64 KiB. Both forms require numeric `callId`, `calltype`,
`duration`; misscall additionally requires numeric `reason`, while the observed
calltime form has no reason field. These values are not interpreted or published: status/mode remain
unknown; call ID, native status and duration remain null. No ringing/answered
transition or one-observation-per-call guarantee follows from this mapping.
Only direct/all-direct and exact-direct selectors are supported by the call
profile. Group selectors are rejected by the executable input contract. Other
call-like actions and groups remain unverified and are not assigned a call type.

Live/replay recognized call records enter only the activity ledger. Silent
history/preload skips these records without Events or message/novelty facts.
Call fingerprint identity uses the exact typed conversation, message ID, actor,
source timestamp and the exact recognized action, independent of processing
time/source. Thus the same record cannot collide across the two action forms,
and the existing misscall identity remains unchanged.
Before a first call insert, the store checks its private native message ID
against existing typed message identities. A prior message projection creates
only an expired, empty-payload activity tombstone, preventing replay from sending
a second notification for the already retained unknown message. Old message
rows, callback bytes and processing cursors are not rewritten.

Reaction observations have passed the targeted direct-chat checks documented in
the [checkpoint](../rich-content-implementation-checkpoint.md). The call
discriminator is proven against a retained source; delivery of a fresh native
call activity remains a separate live-acceptance gate.

“Observed” describes protocol observations, not guaranteed call lifecycle
completeness. The [reaction payload](reaction_v1.payload.json) and
[call payload](call_v1.payload.json) use a discriminated `family` and exactly one
nested `reaction` or `call` detail. They never contain `first_incoming`.
Selectors reject `first_incoming_only`, including explicit false; scope,
direction, collection policy and principal boundaries remain enforced.

Reaction action stays `unknown`: the pinned upstream shape does not reliably
distinguish add/update/remove. A nonempty icon does not prove addition; an empty
icon does not prove removal. Live/replay namespaces and self direction are
preserved; mixed direct/group replay batches are processed separately. Reaction
channels apply cancellation-aware backpressure instead of evicting earlier
observations. This is an in-process delivery guarantee, not durable upstream
replay or recovery of observations never received from Zalo.

Each observation has an opaque `source_id` and `identity_basis` distinguishing an
upstream action ID from a best-effort observed fingerprint. Fingerprinting cannot
prove whether two identical, ID-less upstream observations are two distinct
real-world actions: disclose this limit, never advertise exactly-once semantics.
The stable local envelope ID identifies the retained observation, not a message.
Repeated protocol reports must not mint a new ID on each callback retry.

Call status/mode/duration stay unknown/null until a specific upstream mapping is
supported by evidence. Presence of an enum member does not assert its support.
Reaction target IDs may be absent (empty list) without inventing a target from
nearby messages; metadata and authorization belong to the observed conversation.
Historical preload/archive import does not create these observations.

For a native reaction reference without a positive global ID, the adapter carries
its positive client ID as bounded internal metadata (not a v1 wire field). At
first persistence the store may resolve it through already available message
metadata, in the exact typed conversation, only when there is one distinct
visible global message ID. Missing, ambiguous, recalled or expired candidates
remain unresolved; nearby text/time/name is never a substitute. A supplied global
ID takes precedence over its paired client ID. Combined targets are distinct,
sorted and bounded to 16; invalid/overflow input is rejected rather than truncated.
No history fetch is triggered. Migration 17 adds private client-ID aliases for
newly observed native messages of any supported content/typed conversation.
The alias is not quote metadata and never grants send/quote eligibility.
Already available legacy direct-text quote IDs remain a lookup source. Earlier
media/group rows whose client IDs were lost cannot be reconstructed by guessing;
the current installed v16 candidate still has only the direct-text path until
the migration-17 candidate is verified and deployed.

Aliases are bounded, never truncated, and inserted in the same transaction as
their message. Matching replay can fill a missing alias only for the same typed
conversation/global ID/sender/timestamp and a visible, nonexpired/nonrecalled
message. A conflicting repeat does not replace the original alias; a bounded
private counter records it without IDs. Physical message removal cascades to
the alias. Lookup considers all matching aliases and legacy quote metadata;
multiple distinct targets or contradictory alias/quote IDs are unresolved.
Silent import remains silent and archive records never acquire quote authority.

Fallback source identity includes unresolved native client references before
local resolution and remains independent of later corpus enrichment. Resolution
and first insertion share a transaction. Replayed observations never rewrite a
previously retained source or signed delivery to add a subsequently known target.

Upgrade compatibility also checks the earlier candidate's fingerprint (which
omitted client-only references). If that source or its expired tombstone already
exists, replay is suppressed without rewriting it. That older, weaker identity
cannot distinguish otherwise identical ID-less observations differing only in
client references; conservative suppression preserves its existing ambiguity.
New observations use the stronger identity. Native action-ID observations keep
their original identity unchanged.

## Activity source ledger and retention

Migration 16 adds independent AUTOINCREMENT `activity_observations`, its fanout
watermark, and nullable `event_deliveries.activity_seq`. Subscription activation
captures the activity high-water mark atomically. Fanout commits outbox entries
and progress together, shares the existing queue capacity budget, and filters by
profile, scope, direction and activation boundary. Message fanout excludes
activity profiles. No activity creates messages, FTS, quote anchors, message
identities, conversation catalog entries or first-incoming facts.

Journal and delivery authorization use the observation's conversation even when
target messages are unknown. Missing/expired observations do not fall back to a
subscription's identity. Retention uses local source insertion time, not the
possibly older upstream occurrence time. Expiry erases source/outbox payloads,
cancels pending deliveries, and leaves an explicit journal gap and permanent
identity tombstone: replay cannot resurrect the observation. Acknowledgement
accounts for this gap under the existing ordered receipt policy. Retention zero
keeps the source indefinitely; permanent identity tombstones still consume space. Empty legacy-call suppression markers retain identity only. Their payload is
an empty string; maintenance canonicalizes the preceding exact `{}` marker only
for expired call rows without any linked delivery, independently of age retention.
Other expired payloads remain intact and continue to block downgrade. The rollback
guard is read-only and never performs this maintenance.
Historical preload/archive imports do not enter this ledger.

For an operator cutover, follow the [v3 migration procedure](../rich-content-migration.md).
The existing consumer is not switched by discovery or installation.

## Deployment checkpoint

Message metadata migration 15 is additive (`messages.content_json`); migration 16
is additive too. Previous readers select explicit columns. SQL compatibility is
necessary but insufficient: old event encoders cannot consume new profiles.
The native candidate is installed; the existing production v2 subscription is unchanged.
Two separate incoming-only local test subscriptions are prepared. See
[deployment evidence](../rich-content-candidate-deployment.md).

### Author-text projection and legacy compatibility

`content.text_role` is machine-readable: `author`, `none`, or
`legacy_projection`. New typed reads and v3 return empty text/excerpt for
`none`; attachment title remains an element label. Text-only emoji has role
`author`. A retained record with missing original type has role
`legacy_projection`, which explicitly forbids treating the projection as proven
author text. Legacy/v2 encoding retains its historical text projection and signed
old payloads remain unchanged. The existing plain-text resource is a legacy text
projection; a v3 nontext event does not point to it. V3 content resources return
structured metadata and the explicit role.

### Rollback precondition and proof

Before downgrade, unload the LaunchAgent and keep the service stopped through
binary replacement. Run the candidate owner's command
`zl-mcp -config /absolute/path/config.toml check-rollback`. It takes the account
lock, opens SQLite read-only without migration/session access, and returns counts
only. It refuses downgrade if unsupported profiles remain active, unsupported
work is pending/sending or unacknowledged, or unexpired activity source remains
unfanned. Retained source/outbox activity payload also blocks downgrade: the old
runtime cannot enforce its retention even after fanout/ack. The lock is released on command exit; its report is invalid after any
new write. A lock held by a running service causes refusal.

**Do not start the old binary with active v3 or activity subscriptions.** Its
fanout can consume unsupported work as terminal `invalid_payload`. Reconcile
subscriptions, retained work and checkpoints first; if the guard refuses, keep
the new runtime and fix forward. Inactive subscriptions with unacknowledged
unsupported work can also prevent downgrade; this guard does not promise a
lossless automatic reverse migration. Never clear receipts or restore an older
backup merely to pass it.

The opt-in `TestLegacyRuntimeReferenceCompatibility` runs actual encoder,
store, fanout and journal/ack code from revision
`754f91056f853c8bc88a73821bef4a58a643e225` in an isolated source archive on two
temporary new-schema databases. The compatible case preserves metadata and
expired activity dedup tombstones through old writes and acknowledgements; a negative control
reproduces `invalid_payload` for active v3. It passed before deployment. This is
cross-version code execution, not a test against the running production service.
Re-run with `ZL_ROLLBACK_REFERENCE_ROOT=/absolute/temporary/source/archive` and
`go test ./internal/storage -run '^TestLegacyRuntimeReferenceCompatibility$' -count=1`.
A stopped, verified production backup and post-upgrade checkpoint comparison
are still required; this temporary-state proof does not replace them.

Reaction targets are limited to 16 distinct global IDs, at most 64 Unicode code
points each (current native SDK decodes decimal int64 IDs). This keeps even
maximally escaped valid observations within journal recovery budget; do not
expand that limit independently of envelope/read/ack byte-budget tests.


## Trusted local exact-record preload probe

`probe-preload` with no selector retains its existing aggregate-only behavior.
An optional exact typed conversation/message selector is contract-validated and
examined only in the bounded preload response from the existing session. The
result exposes no selector IDs, text, URLs, param values or credentials. Only fixed allowlisted action/type tokens and at most 32 sorted allowlisted
param-key names are returned. Unknown action/type values expose only presence;
unknown param keys expose only a count and `keys_truncated`. There is no arbitrary
lexical-token output. The diagnostic vocabulary is not a proven call mapping:
matching a word such as `call` never establishes a call status. No param values,
raw object or token hashes are saved or logged.
Multiple exact matches are ambiguous and expose no shape. No match does not
establish absence from Zalo history. This owner-only diagnostic is not an MCP
tool, does not ingest or emit events, start a listener or request phone sync.

The optional `param_shapes` object describes only present keys from the fixed
call/media vocabulary enumerated in `cli_probe_preload.output.json` (including
`callId`, `calltype`, `duration`, `reason`). Each descriptor contains a JSON
`type` and `empty`: null has `empty=true`; strings/arrays/objects use exact
zero length; numbers/booleans have `empty=null`. Missing keys are omitted.
No values, nested keys, lengths or parameter-value hashes are returned. These descriptors prove
structure only, not call classification, status or duration units.

The diagnostic action allowlist also includes `recommened.calltime`,
`recommened.misscall`, `recommened.groupcall`, grounded in the linked first-hand
forensic investigation. Their inclusion enables exact-match investigation only;
it does not enable a call source or map numeric statuses. Arbitrary actions
remain withheld.

## Unsupported-content diagnostic count

Periodic `zalo_persistence_diagnostics` logs expose
`counts.direct.unsupported_content` and `counts.group.unsupported_content`.
These atomic per-open-store counters count admitted normalized unsupported
content attempts, including replay duplicates and failed writes. Excluded
conversations and legacy projections are not counted; they do not denote unique
persisted messages and reset on process restart. No reason strings, content or
identities form metric labels. Raw frame decode failures remain covered by the
existing SDK decode-error counters. No new MCP response field is introduced.

## Bounded media-shape preparation

The exact-record diagnostic descriptor also accepts the fixed outbound-SDK key
names `desc`, `width`, `height`, `fileName`, `fileSize`, `totalSize`, `extention`,
`groupLayoutId`, `isGroupLayout`, `idInGroup`, `totalItemInGroup`. These names
come from the retained send-message/send-voice implementation, not from arbitrary
source keys; their presence does not establish incoming semantics. Type and
emptiness rules are unchanged. Two optional diagnostic booleans compare nonempty
attachment title with description or string params.desc; no text is returned.
Equality is structural evidence, not an author-caption classifier.

For existing live non-text projection logs, `content_shape` contains this same
closed bounded descriptor or null. It has no field values, filenames, lengths,
URLs, arbitrary keys or token hashes. Message JSON/persistence still excludes
the ephemeral diagnostic object. It is ordinary privacy-bounded shape logging,
not sensitive raw native payload capture. The action allowlist additionally
includes the externally grounded recommened.link/recommened.user strings for
investigation only; neither enables a new rich classifier by itself.
