# Задача: завершение приёмки, Strangers и удобное исследование переписки

Дата: 2026-10-03. Статус: в работе; проверенные этапы и открытые критерии отражены в [отчёте приёмки](conversation-completion-acceptance.md). Этот документ задаёт полный объём задачи, а не подтверждает завершение. Актуальные открытые критерии: [open gates](conversation-completion-open-gates.md). Сверка каждого требования: [актуальный аудит](conversation-completion-current-audit.md).

## Результат

Дополнение от 7 октября: пользователь запросил сохранённый архив для повторного
исследования дат до 6 октября без постоянных phone sync. Требования и подтверждённый
объём всего аккаунта описаны в [задаче сохранённого архива](task-retained-mobile-archive.md).
Это не подтверждение реализации или полноты истории и не снимает критерии ниже.

Завершить оставшиеся проверки новых возможностей `zl-mcp`, установить и устранить причины недоступности диалогов Strangers, обеспечить удобный путь «найти собеседника → просмотреть переписку за период → уточнить поиском → прочитать контекст». Добавить загрузку доступной истории с точным отчётом о результате и ограничениях. Актуализировать контракты, документацию и оба skills, проверить установленное подключение и опубликовать изменения.

Сохранить единый постоянный Go-сервис, внутренний collector, существующую сессию, корпус, журнал отправок и границы подписок. Исходники остаются на месте; runtime расположен вне iCloud. Туннель относится к инфраструктуре подключения. Второй listener для того же аккаунта не запускать. Новые модельные evals и переход на Node/Python runtime в эту задачу не входят.

Основание: [приёмка личных сообщений](direct-messaging-acceptance.md), [предыдущая задача](task-direct-messaging.md), [исследование каталога и истории](conversation-discovery-history-research.md). Требования предыдущей задачи сохраняются; здесь объединены её оставшиеся проверки и новые улучшения.

## 1. Завершить оставшиеся проверки

Сначала сверить актуальный установленный бинарник, локальные capabilities и каталог реального клиента. Приложенный пользователем результат подтверждает получение уведомлений помощником; не требовать повторения уже подтверждённого сценария ради нового отчёта. При этом имеющиеся записи испытаний отправки относятся к исходящим событиям v1 и сами по себе не закрывают фильтры v2.

| Проверка | Что установить | Критерий приёмки |
| --- | --- | --- |
| Discovery v2 | Наличие `zalo.conversation.message.created.v2` у сервера и в фактическом клиенте | Одинаковая схема/фильтры через действующее подключение; отсутствие на одной стороне диагностировано по фактам |
| Incoming-only | Входящие принимаются, собственные исходящие исключаются | Подписка с `direction=incoming` доставляет подходящее входящее; исходящее не создаёт доставку для неё |
| First incoming | Первое локально известное обращение и повторное обращение, в том числе после restart | Один факт первого обращения; повтор и replay не сбрасывают признак; `null` не трактуется как `true`; старый собеседник не считается новым |
| Реальная отправка без записи в корпусе | Точный разрешённый peer ID, отсутствующий в локальном каталоге/корпусе | Установлен фактический исход: принятие Zalo с ID либо корректное ограничение upstream; запись контакта не создаётся искусственно для прохождения теста |
| Новая обработка acknowledgement | Числовой/строковый ID на plain/quote routes | Синтетические encrypted HTTP проверки плюс отдельно разрешённая live-проверка исправленного бинарника; существующий `unknown` не переписывается по совпадению текста |
| Повторы и восстановление | Отправка и Events после потери ответа/restart | Прежний UUID сохраняет результат без второй отправки; повтор callback не создаёт повторного уведомления в поддерживающем checkpoint клиенте |
| Skills и транспорт | Фактически установленные версии и подключение | Обновление/reload обоих skills проверено; HTTP capabilities подтверждены; STDIO tools/resources проверены через установленный сервис, без обещания Events через STDIO |

Сначала переиспользовать существующие автономные проверки и доказательства. Новые тесты добавлять для новых требований и обнаруженных дефектов. Для live-отправок заранее зафиксировать точного получателя, текст, UUID и цитируемый anchor; прежнее разрешение на два сообщения не разрешает новые сообщения. Получение подходящего естественного входящего не требует отправки от имени пользователя. Временные подписки имеют согласованный scope и отменяются по завершении проверки.

Отдельно фиксировать принятие upstream, сохранение сообщения, HTTP-доставку callback и обработку помощником. Статус `sent` не означает прочтение; `connected` не означает полную историю. Известный чужой аккаунт и первый локально обнаруженный peer — разные понятия. При невозможности live-сценария записать конкретный незакрытый критерий, не заменять его синтетическим доказательством.

## 2. Strangers: сначала интернет-исследование, затем код и протокол

### Порядок исследования

1. Проверить официальную справку Zalo о сообщениях от незнакомых, настройках приёма и синхронизации. Проверить актуальные upstream исходники, issues/PR и реализации личных аккаунтов: live-обработку, replay, каталог диалогов, специальные inbox и direct history. Для каждого вывода указать URL, дату и commit, разделить документированное поведение, авторское сообщение о live-тесте и нашу гипотезу.
2. После этого проследить соответствующие пути в pinned `zcago` и нашем сервисе: frame → decode → normalize → collection policy → persistence → catalogue → MCP read → Events. Проверить полноту моделей ответа и сохранение continuation/filtering metadata. Не делать вывод о фильтре Strangers только по отсутствию имени.
3. На существующей сессии подтвердить источник Strangers и стабильный peer ID, доступные методы каталога/истории и условия получения. Использовать счётчики и обезличенные метаданные; не публиковать payload, тексты, cookies, токены и signing secrets. Не добавлять пользователя в друзья и не менять настройку приёма как скрытый способ устранить дефект.
4. Проверить отдельно новое входящее от non-friend и восстановление уже существующего диалога/старого сообщения. Для исторического пользовательского случая установить идентичность peer и либо восстановить доступные записи, либо доказать конкретное ограничение источника. Не ждать нового сообщения вместо исследования отсутствующей старой переписки.
5. Зафиксировать исполняемые контракты, затем реализовать найденный путь и регрессионные тесты. Если источник недоступен, вернуть понятное ограничение; не выдавать частичный каталог за полный и не объявлять Strangers поддержанным без live-доказательства.

### Исходные факты интернет-исследования

- [Официальная справка Zalo](https://help.zalo.me/huong-dan/chuyen-muc/bao-mat-va-rieng-tu/chan-tin-nhan-tren-zalo/) описывает отдельную категорию сообщений от незнакомых и настройку их приёма. Это подтверждает поведение продукта, но не описывает API синхронизации этой категории.
- [Справка о Zalo PC](https://help.zalo.me/huong-dan/chuyen-muc/zalo-cong-viec/zalo-app-va-zalo-pc/) описывает синхронизацию штатных клиентов. Это не доказательство полноты данных неофициального listener.
- В проверенном [JS listener](https://github.com/RFS-ADRENO/zca-js/blob/dadfef18bcac53537741855c99f084152da1fad9/src/apis/listen.ts) обычные direct/replay пути не требуют дружбы. Полный inbox Strangers и персонифицированная история этим не доказаны.
- [Открытый PR #370](https://github.com/RFS-ADRENO/zca-js/pull/370) предлагает новый endpoint групповой истории с пагинацией; автор сообщает о live-проверке. Это кандидат для нашего исследования, а не подтверждённый direct-history API.

Сопоставление с текущим кодом: friendship-фильтра в обработке direct не найдено; каталог читается из локальной БД; контакты отдельно не синхронизируются; replay запрашивается без ID чата и без обхода следующих страниц. Полная личная история и отдельный источник Strangers пока не установлены. Подробности и исходные агрегаты — в [исследовании](conversation-discovery-history-research.md).

## 3. Удобства MCP: контракты до реализации

### Просмотр сообщений конкретного чата за период

Добавить `zalo_list_conversation_messages` с плоскими параметрами: `conversation_type`, `conversation_id`, `since`, `until`, `limit`, `cursor`, `order`. Тип и ID обязательны; остальные поля имеют документированные значения по умолчанию. По умолчанию `limit=20`, максимум 50. Интервал `[since, until)`, даты RFC3339; порядок `asc`/`desc` с детерминированным tie-breaker. Неоднозначные даты не угадывать.

Это локальный browse без поискового слова и без скрытого запроса истории. Стабильный snapshot cursor связан с фильтрами и порядком; новые вставки не меняют уже открытые страницы. Возвращать IDs, автора, направление, время, короткий текст, признак обрезки и выданный сервером resource URI для полного текста. Сохранить действующие search/context tools без несовместимых изменений.

### Поиск собеседника среди контактов и диалогов

Расширить существующий каталог поддерживаемыми источниками, вместо добавления нескольких почти одинаковых поисков. Различать контакты без наблюдавшейся переписки, обнаруженные диалоги и записи доступного upstream inbox. Сливать по typed ID, сохранять provenance, alias/name, отношение friend/stranger/unknown только при наличии доказательства, дату refresh и частичный результат.

Нормализовать Unicode и регистр; accent-insensitive сопоставление выдаёт кандидатов, не устанавливает тождество людей. Для одинаковых имён вернуть варианты с IDs. Поддерживать ограниченные страницы и серверный refresh через общий сервис. Отдельно сообщать полноту каждого источника; список друзей не считать всеми чатами. Включить Strangers, когда найден и проверен соответствующий upstream источник. Не обещать глобальный поиск всех пользователей Zalo по имени.

### Загрузка доступной истории

После установления реальных API добавить ограниченную операцию загрузки выбранного диалога: точный typed ID, желаемый интервал, лимиты страниц/записей и постоянный `request_id`. Сразу возвращать `operation_id` и состояние; отдельное чтение статуса показывает progress, полученные границы, количество новых/повторных записей, continuation и причину остановки. Повтор request ID не запускает вторую загрузку; изменённые аргументы дают conflict. Определить отмену, resume, сроки хранения операций и ownership в контракте до реализации.

Не блокировать MCP на долгой загрузке. Сохранить bounded paging, backpressure, дедупликацию, точные ID без float64, устойчивость к повторному cursor, upstream errors и restart. Реализовывать только доказанные методы; для неподдерживаемого direct history возвращать `unsupported`, не подменять его group API или импортом из неизвестного источника.

В каждом результате различать requested interval, observed record bounds, известные gaps, серверное исчерпание страницы и доказанную полноту. Min/max timestamp не означают непрерывное покрытие. Пустая страница не доказывает отсутствие переписки. Отдельные причины: неизвестный чат, отсутствуют локальные записи, нет записей в периоде, upstream недоступен, метод не поддержан, достигнут лимит.

Events-политика согласована 4 октября 2026 года: явный исторический импорт сохраняет сообщения без Events и уведомлений (`notification_policy=none`). Они доступны через просмотр, поиск и контекст. Текущий live/replay после обрыва связи сохраняет прежнюю семантику и может доставлять старое по `sent_at` сообщение, впервые сохранённое после активации подписки. Исторический импорт регистрирует постоянную идентичность, поэтому её последующий live/replay не создаёт новое событие; существующие first-incoming факты не меняются, ранее неизвестный исторический direct peer получает неопределённую новизну, а не положительный first-only факт. Исполняемые схемы и границы реализации: [контракт импорта](contracts/history-import-operation.md). Наличие схем не означает доступность инструмента или источника direct/Strangers history.

## 4. Применение лучших практик MCP и Agent Skills

Использовать предоставленные `mcp-tool-best-practices.pdf` и `mcp-skills-best-practices.pdf` как рекомендации к проектированию. Они не заменяют требования пользователя, исполняемые контракты и существующую серверную модель разрешений. Модельные evals, предлагаемые в PDF, исключены из этой задачи по ранее согласованному ограничению.

| Принцип | Применение и проверка |
| --- | --- |
| Понятные узкие tools | Описать назначение, когда применять, границы локального/сетевого чтения и результат. Browse, поиск и запуск backfill различимы; не создавать generic `action/data` и обёртку на каждый upstream API |
| Простые параметры | Плоские поля, enum, defaults, примеры форматов, лимиты и `additionalProperties=false`. Имена typed identity совпадают во всех tools. Допустимые преобразования типов закрепить явно в контракте; даты и ID не угадывать |
| Tools/resources/skills | Tools дают доступ/операции, resources — полный текст, skills — порядок исследования и обработки Events. Ни credentials, ни SQL/browser обход MCP в skills |
| Меньше вызовов и контекста | Каталог возвращает достаточно метаданных для выбора; browse сразу выдаёт пригодные excerpts и coverage. Полный текст читается только по необходимости; bounded pages вместо выгрузки всей переписки |
| Структурированный результат | Исполняемые input/output JSON Schema; `structuredContent`, `has_more`, cursor, truncation/resource URI и coverage. Пустой результат отличим от ошибки |
| Исправимые ошибки | `isError=true`, стабильный код, безопасное пояснение и следующий допустимый шаг. Никаких credentials, stacktrace или сырых upstream payload |
| Правильные annotations | Проверить фактические `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`; импорт локально пишет данные и не маскируется под чистое чтение. Аннотации не заменяют авторизацию |
| Повторы и длительные операции | Серверный журнал request/operation ID, ограниченные работы, status/progress и restart; ownership каждого ID/cursor/resource проверяется сервером |
| Совместимость discovery | Детерминированный tools list; совместимые добавления; уведомления об изменении каталога при поддержке клиентом. Проверить фактическое обнаружение через клиент, не полагаться на наличие схемы в бинарнике |
| Недоверенная переписка | Тексты, имена и метаданные не разрешают отправку, чтение credentials, изменение подписок или маршрута данных. Ограничения enforce в сервисе; аудит пишет безопасные метаданные, не весь private body |
| Узкие skills | Сохранить разделение исследования и обработки Events. Ясные trigger descriptions, зависимости, fallback при отсутствии capabilities; краткий SKILL.md и ссылки на reference одним уровнем |
| Workflow вместо дублирования схем | Исследование: определить диалог → проверить покрытие → просмотреть период → уточнить поиском → прочитать контекст → ответить с источниками. Events skill отражает v2 и backfill semantics, не копирует JSON Schema |

Описания tools и навыков должны совпадать с реализованными capabilities. Не объявлять новый browse/history доступным до реализации и обновления discovery. Существующие правила отправки/вступления сохранить; новые preview/approval механизмы не вводить автоматически из примера PDF.

## Критерий завершения

Незакрытые критерии прежней задачи имеют актуальный доказанный исход; доступные Strangers сообщения и каталог проходят через исследованный путь; сообщения чата за период доступны без keyword; доступная загрузка истории имеет bounded paging и честный coverage. Пользовательский исторический случай восстановлен либо сопровождается доказанным ограничением конкретного источника. Неопределённая причина потери, непроверенная live-возможность или неподтверждённая полнота не считаются закрытым критерием.

Документация, схемы, source, установленный бинарник и skills согласованы; публикация и CI проверены. Если upstream не предоставляет нужные данные, явно выделить оставшееся ограничение и согласовать уменьшение результата, не объявлять исходную цель достигнутой самостоятельно.
