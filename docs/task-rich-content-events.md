# Задача: содержательные события сообщений, звонков и реакций

Дата: 2026-10-15. Статус: native-кандидат развёрнут, live-приёмка и финальная приёмка функции ещё не завершены.
Текущая матрица приёмки: [acceptance](rich-content-acceptance.md).
Протокол обновления и сохранности данных: [candidate deployment](rich-content-candidate-deployment.md).

## Результат и границы

Устранить необъяснимые пустые Events при нетекстовом содержимом. Сохранять тип и доступные структурированные сведения от Zalo через нормализацию, корпус, reads, ресурсы, журнал подписки и callback. Звонки и реакции должны иметь отдельную семантику и подписки, а не маскироваться под новые сообщения. Обычный текстовый emoji остаётся текстом. Фото, стикер, голосовое, видео и файл остаются сообщениями даже без подписи.

Сохранить единый Go-сервис, текущую сессию, архив, идентичности сообщений, подписки, журнал отправки и подтверждения обработки. На этапе подготовки задания live-отправки, звонки, изменение рабочих подписок и развёртывание не выполнялись. Последующая цель пользователя разрешает реализацию и обновление сервиса после проверки; конкретные live-отправки/звонки и переход рабочей подписки согласуются по подготовленному сценарию. OCR, распознавание речи, автоматическая загрузка медиабайтов и отправка вложений не входят в объём. Новые модельные evals не нужны.

Основание: пользователь наблюдает события при звонках и пустые события при «смайле» и фото без текста. Предыдущее объяснение о реакциях было гипотезой: код реакции сейчас игнорирует. Не считать пользовательский «смайл» доказательством конкретного upstream-типа.

## 1. Что установлено на реальных данных

Read-only снимок установленной SQLite и существующего Events trace на 15 октября. В публичную документацию включены только агрегаты; содержимое, имена, ID, URL и секреты не копировались.

| Наблюдение | Результат | Что оно доказывает |
| --- | --- | --- |
| Сохранённый корпус | 92 записи; 8 с пустым `text` и `attachments=[]` (7 live, 1 replay) | Потеря представления содержания есть до доставки |
| Остальные проекции вложений | 3 записи `["webchat"]`, 1 `["chat.recommended"]`, все с текстом | Сейчас поле содержит исходный тип, а не нормализованную модель вложения |
| Сохранённые доставки | 44 строки v2 в состоянии `delivered`; 1 с пустым текстом | Пустое содержание реально попадало в delivery, это не только гипотеза по UI |
| Сопоставление пустой доставки | Точный message/conversation ID совпал с live-записью корпуса: текст пуст, вложения `[]` | Дефект прослеживается от корпуса до сериализованного callback |
| Существующий trace | 38 распознанных event-body, из них 2 с пустым текстом | Есть независимый след отправляемых тел; число тел не равно числу уникальных сообщений или успешных уведомлений |
| Поля всех 38 тел | Только текущие поля v2, без типа содержимого и вложений | Получателю неоткуда узнать, что за нетекстовое содержимое пришло |
| `message_events` | На момент чтения таблица пуста | Исторические строки нельзя восстановить из неё; использованы сохранённые deliveries и trace |

`delivered` означает серверный результат доставки, а не доказательство того, что модель получила payload или уведомила пользователя. Старая проблема входа автоматизации и workaround через read/ack журнала описаны в [приёмке восстановления событий](event-recovery-acceptance.md); это отдельный слой.

В сохранённых пустых проекциях нет исходного `msgType`/объекта `content`. Поэтому сейчас нельзя достоверно распределить эти 8 записей на фото, звонки, стикеры и прочее. Сырой вход Zalo из callback не восстановить. Точные payload для этих категорий ещё предстоит получить разрешённой диагностикой; не выдавать синтетические fixtures за live-доказательство.

## 2. Причины в исходном коде при подготовке задачи

Ниже диагностированная исходная версия. Текущие исправления и незакрытые пункты —
[implementation checkpoint](rich-content-implementation-checkpoint.md).

1. [Content.UnmarshalJSON](../third_party/zcago/model/message.go): объект признаётся `Attachment` только при `attach.Title != ""`. Объект вложения без заголовка обычно попадает в `Other`. Есть также отдельные `String`, `DeletedContent`, `Other`; `null` требует самостоятельного теста, поскольку Go JSON decoder может принять его в строковую переменную без ошибки.
2. [convertMessage](../internal/zalo/adapter.go) обрабатывает только `String` и `Attachment`. Для `Attachment` берёт `Title` как текст, сохраняет только `MsgType` в `AttachmentTypes`. `Other` и `DeletedContent` не получают содержательной проекции. Исходный `MsgType` теряется у строковых и прочих вариантов; метаданные/подпись/title не разграничены.
3. [domain.Message](../internal/domain/model.go) содержит текст и список типов, но не полноценную модель содержимого. [Хранилище](../internal/storage/conversation_migration.go) сохраняет эту уже обеднённую проекцию.
4. [MessageEncoder.Encode/EncodeProfile](../internal/events/message.go) не включает даже `AttachmentTypes` в legacy/v2 payload. [JSON Schema v2](contracts/conversation_v2_event.delivery.json) допускает пустую строку и закрыта для произвольных новых полей. Исправление только декодера недостаточно.
5. [Listener](../internal/zalo/events.go) читает и игнорирует `Reaction()`/`OldReactions()`. [zcago router](../third_party/zcago/listener/router.go) декодирует реакции отдельным путём. Не объяснять пустую доставку реакцией без доказательства альтернативного message-path.
6. Отдельного классификатора звонков в исследованном message-path нет. Утверждение о конкретном wire-типе/статусе звонка пока не доказано. Не классифицировать по пустоте текста или эвристике по пользовательской фразе.

## 3. Сначала контракт и реальные формы входа

До изменений поведения описать исполняемыми JSON Schema нормализованные сообщения и отдельные reaction/call events, каталог событий, subscribe filters, ответы reads/context/resources и journal read/ack. Зафиксировать таблицу: upstream `msgType` + форма content → тип события/контента → сохранённые поля → допустимые потери/неизвестность. Для каждого mapping указывать основание: реальный обезличенный пример, код upstream или синтетический тест; одних названий типов недостаточно.

Для недостающих примеров использовать существующие приватные исходные артефакты, если они есть. Иначе подготовить ограниченную диагностику текущего listener: форма/ключи, исходный тип, ветка декодера, итог классификации и correlation на локальную запись; без текстов, ссылок вложений, ID и секретов в обычных логах. Полный чувствительный payload — только при отдельном согласовании, локально с ограниченными правами и сроком хранения. Не запускать второй listener и не просить повторять уже доказанные сценарии. Ожидание действий пользователя без временного окна. Исследование этой задачи не требует phone sync.

### Целевая модель

- Сообщение: `content_kind` (`text`, `image`, `sticker`, `audio`, `video`, `file`, `link`, `contact`, `location`, `mixed`, `unsupported`), ограниченный список элементов, сохранённый безопасный upstream type, явная доступность/причина неполноты. Имена полей окончательно закрепить в схемах до реализации.
- `text` — текст автора/подпись только при доказанном соответствии источника. Title файла, описание ссылки и техническая заглушка не становятся речью автора. Отдельный `content_summary` может содержать «Фото без подписи», но явно помечается как системное описание.
- Метаданные allowlist: вид, MIME/имя/размер/длительность/размеры/стикер-ID только если доступны и проверены; отсутствие — null/явный unavailable, без выдумывания. Не раскрывать токенизированные download URLs и upstream params. Предпочитать локальный scoped resource с проверкой принадлежности/доступа; если байты не сохраняются, не обещать их доступность.
- Неизвестный/повреждённый тип: содержательная `unsupported`-проекция, безопасная причина и диагностический счётчик; не пустой успешный «текст», не бесконечный reconnect всей сессии. Управляющие записи обрабатывать отдельно, не объявлять их пользовательскими сообщениями.
- Unicode emoji, модификаторы кожи, ZWJ и комбинируемые символы сохранять; ограничение существующего текста — 2048 Unicode code points с `text_truncated`/resource. У остальных полей тоже обязательны лимиты, включая количество элементов и общий размер callback.
- Исторические записи с утраченным исходным типом честно помечать как legacy/unknown; не угадывать image/call по `text=""`. Миграция не создаёт Events и не переписывает старые подтверждения.

### Звонки, реакции и подписки

- Отдельные семейства call/reaction, точные имена/версии закрепить контрактом. Для звонка хранить только наблюдаемый upstream-статус/переход; не выводить «пропущен», «принят», длительность и участников из догадки. Для реакции: актор, доступный target ID, значение и add/remove/update, включая неизвестный target.
- Определить стабильную идентичность, дедупликацию и порядок переходов, включая replay/restart, несколько реакций и удаление реакции. Не создавать случайный новый ID на каждый retry; невозможность надёжного сопоставления обозначать явно.
- Call/reaction не расходуют факт `first_incoming` сообщения и не появляются в message-only подписке. Первое реальное входящее фото/стикер считается сообщением и может установить этот факт; фильтры работают по семантике, а не непустому тексту.
- Существующие scope/direction/first-only ограничения сообщений сохраняются. Для call/reaction отдельно определить направление и допустимые фильтры; неподдерживаемый `first_incoming_only` отклонять, не игнорировать. Подписка на сообщения не даёт согласия на новые категории событий.
- Исторический import и archive reads по-прежнему silent. Live/replay сохраняют прежние границы активации и упорядоченный journal/ack; типизация не должна переиздать весь старый корпус.

### Хранение событий без сообщения

Текущий журнал/доступ и retention зависят от `messages`/`message_seq` (см. [event_journal.go](../internal/storage/event_journal.go)). Для call/reaction до реализации определить собственную durable source identity/sequence, атомарную запись и границу активации подписки; не создавать фиктивное сообщение ради существующего JOIN. Явно описать authorization по conversation и principal, срок хранения, tombstones, доступность resources, retry и ack после удаления target. Отсутствующий target не расширяет доступ и не блокирует весь журнал. Проверить вызов/реакцию без corpus row, replay до/после активации, refresh/cancel/restart и очистку retention без потери неподтверждённого события сверх заявленной политики.

### Совместимость

Не добавлять поля молча в закрытые v2/legacy схемы и не менять подписки Ann автоматически. До реализации подготовить версионированный профиль богатых message events и план совместимости reads/resources, явное создание новых подписок, проверку discovery в реальном клиенте, откат. Старые сохранённые payload остаются неизменными для подписи/retry и продолжают читаться/подтверждаться. Старые подписки сохраняют свой контракт до согласованного перехода; отдельно документировать, что в них старое ограничение представления не исправляется автоматически. Удаление старого профиля возможно после проверенного перехода и отсутствия активных потребителей/необработанного журнала, а не в рамках написания этой задачи.

Для cutover зафиксировать границу old/new generations, состояние backlog и processing checkpoints. На перекрытии дедуплицировать по доказанной стабильной source identity между профилями (не предполагать одинаковые event ID); старую подписку отключать после сверки непрерывного покрытия. Порядок «отключить/создать» без reconciliation не принимается: он создаёт gap или повторные уведомления.

План rollback обязан определить совместимость старого бинарника с новой схемой БД. Если миграция необратима — остановленный согласованный backup/restore и способ сохранить/восстановить новые данные и ack за интервал после обновления; простой откат к старой БД с потерей этого интервала не допускается. Старый бинарник не запускать на несовместимой схеме. Проверить rollback на временном состоянии до live-развёртывания.

## 4. Реализация и документация

Порядок: схемы/fixtures → upstream decode и семантический classifier → domain/storage migration → reads/context/resources → fanout/journal/encoder → skill/client integration → проверка установленной версии после согласованного развёртывания.

Использовать общую нормализацию для direct/group, live/replay и доступных history sources, сохраняя различия source coverage и silent import. Не повышать архивные строки до send/quote anchors. Проверить tombstones/recall/TTL: не выдавать удалённые метаданные/контент через новые ресурсы, учитывать уже сохранённые доставки в соответствии с действующей политикой.

Актуализировать [ТЗ](technical-spec.md), [Events](contracts/events.md), [browsing](contracts/conversation-browsing.md), [history](history-import.md), README/руководство подключения и эксплуатации. Обновить оба skills: [обработка Events](../skills/handling-zalo-message-events/SKILL.md) и [исследование](../skills/researching-zalo-groups/SKILL.md), их references/examples. Учить различать caption/summary, emoji/sticker/reaction, неизвестный тип/отсутствие сообщения, доступность вложений; не угадывать содержание фото или речь. Не вводить отдельный tool на каждый медиатип, если задачу покрывают существующие reads/resources. Установленные skills сверить после поставки. Исторические evals не объявлять проверкой новой модели.

## 5. Приёмка реализации

AAA-тесты на исполняемые контракты, поведение и границы, без новых модельных evals:

| Сценарий | Проверяемый результат |
| --- | --- |
| Текст/emoji/ZWJ, длинная подпись | Исходный текст сохранён; корректное усечение и полный resource |
| Фото без/с подписью, несколько вложений | Тип и доступные элементы проходят весь путь; подпись отделена от summary; нет пустого необъяснимого payload |
| Стикер, аудио, видео, файл, ссылка, контакт, геопозиция | Доказанный mapping либо честный unsupported; метаданные ограничены и не заменяют слова автора |
| Реакция add/remove, повтор, неизвестный target | Только reaction-подписка; стабильный target/identity либо явная неопределённость; нет нового message/first fact |
| Звонок и повторные переходы | Только call-подписка; статус соответствует wire evidence, дедупликация без выдуманных переходов |
| null/пустой объект/неизвестный type/ошибка формы | Диагностируемая ограниченная проекция/ошибка записи; коллектор не теряет следующие валидные записи |
| Direct/group, incoming/outgoing, первый peer | Правильные namespaces/direction, первое медиасообщение один раз; calls/reactions не расходуют novelty |
| Callback и journal | Одинаковые event ID/содержимое; точные подписанные байты, localhost и HTTPS политики, retry/restart и ordered/idempotent ack |
| Upgrade/rollback | Старые подписки/очередь/receipt неизменны, discovery новой версии, новые поля согласованы с reads; миграция без уведомлений |
| Silent history/archive/recall/TTL | Нет исторического flood, не раскрывается отозванное/истёкшее содержимое, архивные ограничения сохранены |
| Adversarial metadata | Инструкции в caption/filename/description не становятся авторизацией; лимиты/escaping, нет утечки credentials/download URL |

Сначала автономный стенд со временной БД и локальным подписанным receiver. Затем реальные примеры каждого заявленного поддерживаемого класса через тот же установленный сервис; минимальные недостающие действия пользователя согласовать после подготовки, без лимита окна и без нового аккаунта. Для неоднозначных или недоступных upstream-классов явно оставить незакрытый пункт, а не подменять его fixture. Не требовать ручной проверки уведомления Ann вместо точного серверного журнала; обработку клиентом проверять отдельно от HTTP 2xx.

Окончательные доказательства: контракт/fixture → нормализованная запись → read/resource → journal → подписанный callback → подтверждение обработки. Приватные ID остаются в локальном протоколе; публичный отчёт содержит обезличенные результаты. Root/nested-module test/race/vet запускать по затронутому коду, CI и сборки согласно действующим правилам проекта.
