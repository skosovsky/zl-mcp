# Задача: единый сервис Zalo MCP для Ann

Дата: 1 октября 2026 года. Статус: архитектурное направление согласовано, реализация не начата.

## Проблема

Текущий MVP состоит из самостоятельного collector и MCP stdio-процессов. Он рассчитан на локального MCP-клиента. Сбор сообщений работает, но маршрут подключения облачной Ann и доставка событий в неё не реализованы. Добавление отдельного постоянного MCP-процесса поверх collector усложняет персональную установку без установленной необходимости.

## Результат

Один постоянный Go-процесс на Mac объединяет внутренний сборщик Zalo, MCP-интерфейс, управление подписками и доставку событий. Процесс запускается напрямую одним пользовательским LaunchAgent. Python-supervisor не используется. Collector становится внутренним модулем, а MCP — единственной внешней точкой доступа приложения.

```text
Ann ↔ защищённое подключение ↔ zl-mcp service
                                  ├─ MCP tools / subscriptions
                                  ├─ внутренний Zalo adapter / listener
                                  ├─ SQLite: корпус, операции, события, доставки
                                  └─ delivery worker → HTTPS callback Ann
```

Единство процесса не означает смешение ответственности. Обработчики MCP вызывают доменные порты; внутренний collector владеет Zalo listener и сбором. Подписки, callback и ключи доставки принадлежат MCP Events, collector о них не знает. Типы zcago остаются внутри адаптера.

## Связь с текущими задачами

Эта задача заменяет архитектурное направление [task-native-macos-service.md](task-native-macos-service.md), где постоянным сервисом оставался самостоятельный collector. Требования к прямому запуску Go, ожиданию auth_required, ротации логов и безопасному переходу сохраняются и включаются сюда. Не выполнять прежнюю задачу как отдельную миграцию перед этой.

[technical-spec.md](technical-spec.md) и [completion-audit.md](completion-audit.md) описывают реализованный локальный MVP. До реализации обновить ТЗ новой архитектурой и явно расширить scope для Ann/Events. Историческая приёмка не является доказательством готовности этой доработки.

## Сначала проверить подключение Ann

До выбора основного транспорта выполнить небольшой spike с синтетическим MCP-сервером без Zalo credentials и реальной переписки:

1. Проверить доступность Secure MCP Tunnel и developer mode для целевого аккаунта и клиента Ann.
2. Подключить сервер, вызвать tool из целевого чата Ann.
3. Проверить полный цикл Events: discovery → subscribe → callback verification → delivery → реакция Ann → unsubscribe.
4. Проверить, как клиент повторно подключается и обновляет подписку после перезапуска сервера.
5. Зафиксировать подтверждённый маршрут и ограничения платформы. Не считать успешное подключение локального Codex подтверждением доступа Ann.

Secure MCP Tunnel — первый кандидат для персонального подключения без публичного порта. Поддержка tools через туннель документирована; совместимость Events в целевом сценарии требуется подтвердить отдельно. Если маршрут не работает, обсудить альтернативу с пользователем до добавления публичного HTTP endpoint, облачного relay или нового постоянно работающего компонента. Транспорт основного сервиса нельзя выбирать по предположению.

## Контракты и режимы запуска

До реализации зафиксировать контракт основного режима, например `zl-mcp -config CONFIG service`, конфигурацию подтверждённого транспорта и схемы Events. Название команды пока предложено, не реализовано.

- `service` — основной постоянный процесс, один владелец сессии/listener и account lock; несколько клиентских подключений не создают новые listeners.
- `login` — отдельная интерактивная CLI-операция при остановленном сервисе.
- STDIO — дополнительный режим для локального Codex и разработки. Он не определяет жизненный цикл основного сервиса. Если его сохранять как клиентский мост, он должен обращаться к уже работающему сервису по узкому private IPC и не запускать собственный сборщик.
- Старые `collect`/`serve` должны получить явно описанный период совместимости либо удаление после миграции. Не поддерживать две независимые основные архитектуры бессрочно; вычистить ненужный legacy после перехода.

Сохранить контракты действующих tools, allowlist, account binding, одноразовые approvals, request_id/idempotency, rate limits, coverage и resource access. Схемы Events и ошибки сначала описать в docs/contracts; реализация и проверки должны соответствовать им. Не придумывать tools для обхода стандартных event methods.

## Внутренний collector и авторизация

Collector принимает события Zalo и транзакционно сохраняет сообщение и запись внутреннего журнала событий. Upstream replay и дубликат сообщения не создают повторное новое событие. Внешние сетевые вызовы к collector отсутствуют; команды вступления приходят через доменный порт с проверкой approval.

При известном auth failure на Restore или listener сервис остаётся живым: authenticated=false, collector_state=auth_required, NOT_AUTHENTICATED и known gap. Соединение, reconnect и сетевые операции Zalo прекращаются; status и чтение существующего корпуса остаются доступны. Не создавать QR автоматически. Сетевые сбои и неизвестные upstream ошибки не приравнивать к auth failure.

Для нового входа: остановить LaunchAgent → выполнить login → включить сервис. SIGTERM должен останавливать сбор, MCP, delivery worker, закрывать ресурсы и освобождать account lock за ограниченное время. Уже принятые операции и доставки остаются в БД для безопасного восстановления.

## MCP Events и надёжность

Реализовать capability events, events/list, events/subscribe и events/unsubscribe по подтверждённой версии протокола. Сервер управляет постоянными подписками: владелец, фильтры групп, callback, signing secret, expiration и replay cursor, если replay предоставляется. Подписки идемпотентны и ограничены доступными владельцу группами.

MCP Events обрабатывает внутренний журнал и создаёт постоянную очередь доставок. Не полагаться на только in-memory канал между сбором и отправкой. Зафиксировать watermark/транзакции и уникальные ключи так, чтобы падение между записью события и созданием доставок не теряло событие и не размножало задания.

Delivery worker отправляет подписанные HTTPS запросы независимо от обработки входящих MCP tools. Зависший callback не блокирует сбор Zalo. Сохранять eventId при повторе, обновлять подпись и timestamp; ограничивать время запроса, backoff, число попыток и размер очереди. 2xx подтверждает получение платформой, а не завершение задачи Ann. 410/413 не повторять. Отмена, expiration и отзыв доступа прекращают доставку; состояние ошибок доступно для диагностики без секретов.

До отправки данных проверить callback и адрес назначения по требованиям платформы: HTTPS, signed challenge, ограничения адресов, запрет redirect и защита от DNS rebinding. Не передавать session cookies Zalo. Signing secrets хранить приватно, не выводить в tools, traces и логи.

### Открытые решения перед реализацией

Архитектура согласована, но следующие параметры пока не согласованы:

- payload события: только ID/автор/время с последующим чтением контекста либо включение текста;
- event name и schemas, серверные фильтры, срок подписки;
- правила replay при новой подписке и после длительного отключения;
- лимиты очереди, срок хранения заданий и поведение при исчерпании попыток;
- допустимость передачи выбранной переписки в Ann и требуемая доступность Mac.

Зафиксировать решения в ТЗ до зависимой реализации. Не включать полную переписку или бессрочные подписки по умолчанию. Сбор во время сна Mac, полнота истории Zalo и круглосуточная доступность не гарантируются этой архитектурой.

## Установка на Mac

Сохранить согласованные локальные пути: ~/.local/bin/zl-mcp, ~/.config/zl-mcp/config.toml, ~/.local/share/zl-mcp и ~/Library/Logs/zl-mcp. Исходники остаются в iCloud; установленный сервис от checkout не зависит.

Один LaunchAgent напрямую запускает основной Go-режим. launchd отвечает за старт после входа пользователя и восстановление после падения. Go отвечает за ожидание auth_required, graceful shutdown и JSON-логи с ротацией: 5 МиБ и три архива, private permissions. Диагностика ошибок запуска не скрывается в /dev/null без альтернативного sink.

До переключения сохранить предыдущие бинарник, config и plist. Штатно выгрузить старый collector, проверить освобождение lock, заменить бинарник атомарно и включить новый сервис. Сессию, корпус, approvals и операции не обнулять. Python runner удалить только после успешной проверки новой установки. При неуспехе восстановить предыдущие файлы и сервис.

## Критерии приёмки

1. Платформенный spike доказал доступ tools и Events именно из целевого чата Ann; неподтверждённые ограничения записаны, транспорт выбран по факту.
2. Один основной Go-процесс под launchd содержит один listener; несколько MCP-клиентов и повторные подключения не создают дополнительный listener. Collector не имеет внешнего сетевого интерфейса.
3. Действующие tool contracts, approval guards, account binding, allowlist, rate limits, FTS/coverage и идемпотентность вступления сохранены.
4. Контракты Events покрывают discovery, subscribe/refresh/unsubscribe, авторизацию, expiration и callback verification; неизвестные поля и неверные параметры отклоняются.
5. Сообщение и внутреннее событие сохраняются атомарно; дубликаты replay не создают повторное новое событие. Crash recovery не теряет принятые события и задания.
6. Проверены доставка и временные ошибки, стабильный eventId при повторе, out-of-order, expiration, отмена, отзыв allowlist, restart и очередь. Доставка at-least-once в пределах retry/retention policy; exactly-once не обещается.
7. Auth-required при запуске и при потере listener сохраняет живой MCP и корпус без сетевых повторов Zalo. Неисправный callback также не блокирует сбор и чтения.
8. SIGTERM завершает компоненты без зависших операций и освобождает lock; повторный запуск и QR-восстановление сохраняют корпус.
9. Логи ротируются, файлы приватны, stderr/stdout соответствуют транспортам. Нет Python runtime dependency у приложения; удалён ненужный legacy.
10. Проходят релевантные AAA unit/contract/integration tests, go test ./..., go test -race ./..., go vet ./..., сборки macOS arm64/Linux amd64 без CGO. Изменения tools/skill требуют повторных затронутых evals.
11. Проверены реальный MCP status/search/context и тестовое событие в Ann, фильтрация невыбранной группы, unsubscribe и восстановление launchd после падения. Дополнительные live действия с аккаунтом выполнять только в согласованном объёме.
12. Обновлены ТЗ, README, local-connection.md, mac-deployment.md и skill при необходимости. Отчёт отделяет сделанные проверки от неподтверждённых, включая фактическую перезагрузку Mac.
