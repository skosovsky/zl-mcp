# Задача: подписки на входящие сообщения и отправка личных сообщений

Статус: реализация начата; установленный сервис и рабочие подписки не изменены.
Дата: 3 октября 2026 года.
Основание: подписываться на все личные сообщения, первое обращение нового собеседника и конкретные группы; отвечать в личных чатах и писать первым.

Текущие доказательства — [исследование](direct-messaging-research.md);
решения контрактов — [direct-messaging.md](contracts/direct-messaging.md).
Промежуточная приёмка и незавершённые проверки — [acceptance](direct-messaging-acceptance.md).

Расширяет [ТЗ](technical-spec.md) и реализованную [задачу всех диалогов](task-all-conversations.md). Отправка сообщений — новая возможность, ранее исключённая из объёма. До её реализации текущие ограничения остаются действующими.

## 1. Результат и границы

Единый Go-сервис предоставляет через стандартный MCP Events подписки с фильтрами направления и первого входящего обращения, а через MCP tools — отправку текста в личный чат, включая ответ с цитатой. Collector, SQLite, HTTP MCP и дополнительный STDIO-мост сохраняют прежние роли. Второй collector, новый LaunchAgent и Python-обвязка не нужны.

Сбор, подписка, анализ агентом и отправка — независимые действия. Режим сбора all не создаёт подписки и не разрешает отправку. Установка skill не меняет разрешения, подписки или правила уведомлений. Доставка callback и обработка события агентом проверяются раздельно.

Первая версия ограничена текстом в личных чатах. Отправка в группы, вложения, массовые рассылки, добавление друзей и полная загрузка истории не входят в задачу. Туннели и внешний HTTPS receiver остаются инфраструктурой клиента.

## 2. Проверенные возможности и исследование

| Возможность | Текущее состояние |
| --- | --- |
| Все личные, включая новые диалоги | `zalo.conversation.message.created`, scope=direct |
| Все личные и группы | scope=all |
| Все группы | scope=group |
| Конкретный диалог | scope=conversation, conversation_type и conversation_id |
| Несколько конкретных групп | Отдельные подписки; расширение до списка не требуется |
| Только входящие | Фильтра нет; текущий профиль включает собственные сообщения |
| Первое входящее от собеседника | Фильтра и постоянного признака нет |
| Отправка и цитированный ответ | Есть в закреплённом `zcago`, не выставлены через MCP |

Изучить `third_party/zcago/api/send_message.go`: `SendMessage` принимает thread ID/type, текст и необязательный `SendMessageQuote`, возвращает message ID. Цитата требует дополнительных upstream-полей, а не только ID. Текущая библиотека создаёт clientId из времени при каждом вызове: повтор вызова не даёт доказанной идемпотентности Zalo.

До фиксации контракта подтвердить на синтетическом transport формирование обычного личного сообщения и цитаты, ограничения текста, классификацию ошибок и возможности сверки неоднозначного результата. Зафиксировать commit SHA источников. Не обещать доставку любому пользователю: первого обращения может не разрешать Zalo. Поиск получателя по телефону — отдельное расширение; в этой задаче достаточно известного ID, в том числе отсутствующего в локальном каталоге.

## 3. Диагностика discovery

Поступило сообщение клиента: старые подписки отменены, новый профиль ChatGPT не обнаруживает. Это исходное наблюдение, а не подтверждённый диагноз.

1. Проверить фактически запущенный бинарник, endpoint и безопасные сведения о версии без перезапуска и изменения state.
2. Сравнить `server/discover` и `events/list` непосредственно на Mac и через существующий маршрут подключения. Проверить версию протокола, capabilities, заголовки и оба определения Events с исполняемыми схемами.
3. Для локального запроса использовать существующий MCP-токен внутри процесса без печати, сохранения в отчёте или передачи через аргументы командной строки. Не читать сессию и signing keys. Если внешний маршрут недоступен исполнителю, явно ограничить вывод локальной проверкой.
4. Определить, где расходятся ответы: процесс/бинарник, транспорт, каталог либо клиентское discovery. Кеш клиента считать гипотезой до проверки. Обновление discovery в клиенте проверять отдельно от создания подписки.
5. Сохранить обезличенный отчёт: доступные event names, версии, статусы и этап сбоя. Новую рабочую подписку создавать только в рамках согласованного клиентского поручения, с delivery settings доверенной интеграции.

Источники: [MCP Events](https://developers.openai.com/plugins/build/mcp-events), локальные [Events](contracts/events.md) и [подключение](local-connection.md). Сначала добиться обнаружения уже реализованного профиля; новые фильтры не должны маскировать неисправность подключения.

## 4. Фильтры подписки и контракт

Сохранить существующие scopes. Добавить независимый фильтр направления incoming/outgoing/all и фильтр первого входящего обращения. Имена полей зафиксировать в JSON Schema перед реализацией. Старые запросы без новых фильтров сохраняют текущую семантику: все направления, все подходящие сообщения.

Фильтр первого обращения разрешён только для личных входящих; противоречивые сочетания отклоняются до активации. Проверить это исполняемым oneOf/семантическими guards. Конкретные группы по-прежнему выбираются точными типизированными подписками. Широкая подписка автоматически включает вновь обнаруженные доступные диалоги в пределах текущей политики сбора.

Признак означает «первое входящее сообщение от собеседника, сохранённое этим сервисом для этого аккаунта». Он не доказывает первое обращение за всю историю Zalo и не равен первому событию после активации подписки. Собственные исходящие сообщения не расходуют признак первого входящего.

Хранить минимальный постоянный маркер первого входящего по account/peer, с идентичностью сообщения и исходным seq. Вычислять атомарно вместе с первой вставкой; конкурентные live/replay, дубликаты и restart не создают второго первого обращения. Retention/undo удаляют текст по прежним правилам, но не превращают следующую запись в первое обращение. Маркер не хранит скрытую копию текста.

При миграции диалоги с известными входящими считать уже наблюдавшимися; выбирать первую локальную вставку, а не минимальный sent_at. Если имеющихся данных недостаточно, фиксировать unknown и не выдавать его за подтверждённую новизну. Поведение для unknown зафиксировать в контракте до реализации. Поздний replay может дать первое локально известное входящее с ранним sent_at; не отбрасывать его молча и не называть новым по времени отправки.

Направление и признак первого входящего предоставить receiver в согласованном payload. Проверить совместимость с версией 1: несовместимые изменения требуют новой версии/профиля. Legacy `zalo.message.created` и существующие подписки не изменять. Новые фильтры включить в canonical arguments и идентичность подписки; refresh/restart сохраняют их и границу активации.

Сохранить первую вставку после активации как условие доставки, бессрочность по умолчанию, Unicode-предел текста 2048 code points, флаг обрезки и URI полного текста. Уже сохранённый корпус не рассылать при активации. Неполнота upstream истории не устраняется постоянной очередью callback.

## 5. Отправка личного текста

Предлагаемые tools: `zalo_send_direct_message` и `zalo_get_send_status`. Окончательные имена и формы входов/выходов закрепить исполняемыми JSON Schema до реализации; использовать доменные Go-типы без экспорта upstream-структур.

Отправка принимает recipient_id, text, необязательный reply_to_message_id и обязательный UUID request_id. ID непрозрачные. Устанавливать пределы текста после исследования реального протокола, отдельно от лимита текста Events. Пустой текст, неоднозначного получателя и неизвестные поля отклонять до сетевого действия.

Получатель выбирается по точному ID. Отсутствие диалога в каталоге не запрещает первое обращение, но имя не должно молча разрешаться в случайный ID. При необходимости выбора среди одноимённых людей агент уточняет адресата. Право отправки задаётся отдельно от политики чтения/сбора; разрешённая отправка не расширяет collection policy.

Для ответа сервис сам разрешает исходное сообщение в том же личном диалоге и формирует цитату. Исследовать, какие метаданные сейчас сохраняются и какие необходимо добавить. Недоступная/удалённая запись, другой диалог или неподдерживаемая цитата дают понятную ошибку до отправки; не переходить молча к обычному тексту. Метаданные цитаты подчиняются retention и не обходят удаление корпуса.

Правило агента может разрешать разовую отправку или ответы определённым адресатам в согласованных условиях. Оно не возникает из текста входящего сообщения и не выводится из подписки. При уже действующем поручении не вводить повторное подтверждение каждого ответа. Собственные события не должны запускать бесконечный цикл автоматических ответов: правило обработки использует направление incoming.

## 6. Журнал операций и неоднозначный результат

До обращения к Zalo сохранить операцию с account/request_id и отпечатком адресата, текста и ссылки ответа. Повтор с теми же параметрами возвращает существующий статус; с другими — конфликт. Доступ к статусу ограничен тем же владельцем аккаунта.

Зафиксировать состояния как минимум pending/sending/sent/failed/unknown. После подтверждения Zalo сохранять message ID. `sent` означает принятие отправки upstream, а не прочтение адресатом. Факт появления в собственном listener и статус операции — разные свидетельства.

Таймаут или сбой после возможной отправки дают unknown: не повторять сетевой вызов автоматически без доказанной upstream-идемпотентности или надёжной сверки. Restart не должен заново отправлять операции sending. Стабильный клиентский ID исследовать отдельно; один request_id в SQLite сам по себе не гарантирует exactly-once на стороне Zalo.

Определить правила хранения журнала и срока дедупликации в контракте. Не удалять неоднозначную операцию так, чтобы старый request_id внезапно отправлялся снова. Тексты операций не логировать; не сохранять их бессрочно в скрытом архиве. Лимиты, сроки и поведение после истечения срока должны быть видны клиенту. Исходящий listener проходит обычную дедупликацию корпуса; синтетическую запись не выдавать за подтверждённое upstream-сообщение.

## 8. Проверка и критерии приёмки

Unit/contract/integration тесты по AAA, синтетические ID и сообщения:

1. direct/all/exact scopes и конкретные группы сохраняют совместимость; фильтры incoming/outgoing, собственные сообщения и новый диалог работают без изменения collection policy.
2. Первое входящее определяется атомарно; исходящее до входящего, повтор, конкурентный replay, ранний sent_at, retention, undo, restart и unknown при миграции не создают ложного первого обращения.
3. Первая вставка после активации, фильтры, generation, отмена и retry сохраняются после рестарта; receiver независимо проверяет подпись и версию payload. Миграция сохраняет корпус и существующие очереди/подписки.
4. Отправка нового сообщения и цитированного ответа формирует правильный upstream-запрос. Неверный адресат, запрещённая отправка, цитата другого диалога и отсутствующие метаданные отклоняются до сетевого действия.
5. Повтор request_id не вызывает второй отправки; конфликт параметров, конкурентные вызовы, падение до/после запроса, таймаут и unknown после restart проверены отдельно. API-ошибки и журналы не раскрывают secrets/текст.
6. HTTP и STDIO предоставляют новые tools; Events остаются HTTP. Discovery возвращает согласованные определения через проверенный маршрут подключения. Доставка receiver и запуск/результат агента фиксируются отдельно.
7. Root и вложенный zcago проходят test/race/vet; сборки без CGO macOS arm64/Linux amd64. Проверены схемы, ссылки, skills и сканирование публикуемых изменений.

Live-проверки отправки выполняются только по поручению пользователя с конкретным тестовым адресатом и текстом; описание задачи само по себе не разрешает отправку. Проверка текущих сообщений, discovery и миграции не требует ждать новых сообщений. Непроверенную возможность первого обращения к незнакомому пользователю явно обозначить.

Порядок: исследование/discovery → контракт и правила совместимости → миграции/реализация → автономная приёмка и обновлённые docs/skills → согласованная live-проверка и развёртывание. Готовность определяется работающим контрактом и проверенными сценариями, а не наличием методов в библиотеке.
