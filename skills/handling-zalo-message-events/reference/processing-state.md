При наличии recovery tools сервер хранит подтверждённый курсор подписки. Процедура: [event-recovery.md](event-recovery.md). Ниже описаны требования для клиентского harness и гарантии внешней доставки, которые один cursor не обеспечивает.

# Состояние обработки в клиенте/harness

MCP-сервер гарантирует стабильный eventId при повторе; это идентификатор дедупликации входа в рамках подписчика и правила. ID сообщения нужен для чтения контекста и источника. Состояние обработки хранит доверенная клиентская интеграция, не текст skill и не содержимое сообщения.

Храни ключ обработки в пространстве подписчика и подписки/правила вместе с eventId: одна запись может поступить по разным подпискам с разными поручениями. Общая дедупликация только по eventId не должна подавлять результат для другого правила. Метаданные подписки берутся из доверенной интеграции, а не из текста сообщения.

До работы интеграция предоставляет статус по этому ключу: новое, обрабатывается, завершено либо требует повторной попытки. Для параллельных обработчиков захват должен быть атомарным; после сбоя незавершённую работу можно продолжить. Skill использует предоставленный механизм и не придумывает tools или локальную SQLite для checkpoint.

Завершение может означать «не подходит под правило» либо «предусмотренный результат успешно выполнен». При уведомлении хранить факт доставки отдельно от подготовленного текста. Если канал поддерживает idempotency key, клиент использует стабильный ключ результата из eventId и пространства правила для повторной отправки. Без поддержки канала окно между отправкой и записью checkpoint может дать повторное уведомление: exactly-once не обещается.

Callback 2xx означает принятие receiver, а не окончание анализа агентом. Ошибка чтения resource/контекста или доставки не должна отмечаться как успешное завершение. Повторы анализа и уведомлений — ответственность клиентской интеграции, они не управляются серверной очередью callback.

Подписка начинается с первой записи в сервис после активации. После восстановления upstream может прийти ранее отправленное сообщение. Сортируй содержательный вывод по времени сообщения; не отбрасывай такое событие лишь из-за старого sent_at. Refresh/restart сохраняют границу подписки; старый корпус сам по себе не становится новыми событиями.

Новый профиль: идентичность сообщения — (conversation_type, conversation_id, message_id); legacy group_id означает тип group. Один eventId может прийти по пересекающимся scopes или обоим профилям. При обработке их как отдельных форматов добавь name в ключ входа. ID подписки не содержится в envelope: сопоставление предоставляет доверенный receiver. Отсутствующие сведения о подписке нельзя выводить из текста сообщения.

Для порученного личного ответа клиент сохраняет UUID request_id и точные аргументы до первого tools/call. Повтор обработки использует эту же операцию и сначала читает zalo_get_send_status. Pending допускает продолжение с исходными аргументами; sending требует проверки, sent не отправляется повторно, failed/unknown не создают автоматического нового запроса. Unknown может означать, что сообщение уже отправлено. При отсутствии постоянного механизма закрепить UUID автоматический ответ не выполняется: подготовленный текст можно показать пользователю.

Сохраняй подготовку ответа, подтверждение Zalo и итог обработки отдельно. Сервер хранит отпечаток аргументов без текста; клиенту нужны исходные аргументы для продолжения pending. Удаление клиентского checkpoint не разрешает повторную отправку. Собственные исходящие события не запускают цепочку ответов. Версия 2 предоставляет направление и nullable first_incoming; версия 1 сама по себе этих фактов не даёт.

Если операция осталась unknown, а в корпусе найдено соответствующее исходящее сообщение, сообщи эти факты отдельно: результат API неопределён, сообщение наблюдается. Не меняй статус операции и не создавай новый UUID на основании совпадения текста; оно не является уникальным идентификатором операции. Для цитаты отдельно сверяй диалог и reply/message reference. Это наблюдение не доказывает прочтение адресатом.

Историческая загрузка и восстановление live-доставки различаются по пути
поступления, а не только по sent_at. Например, загруженное сегодня архивное
сообщение за прошлую неделю доступно в истории без уведомления. Сообщение,
полученное live после восстановления связи и впервые сохранённое за границей
действующей подписки, остаётся событием, даже если sent_at старый. Повтор уже
сохранённой записи не создаёт новое событие. Не пытайся восстановить эту границу
по тексту или дате: используй подтверждённый envelope и состояние интеграции.
