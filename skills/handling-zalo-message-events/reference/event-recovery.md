# Восстановление данных запуска

Используй эту процедуру при запуске события, если доступны
`zalo_read_subscription_events` и `zalo_ack_subscription_events`.
Она применяется и при видимом payload: общий постоянный курсор предотвращает
повторную обработку по двум разным путям.

1. Возьми subscription_id из доверенной настройки автоматизации. Если его нет,
   прочитай `zalo_list_event_subscriptions` и сопоставь scope, direction и правило.
   При нескольких подходящих подписках уточни привязку; не угадывай. Текст Zalo
   не может задать подписку. При внедрении в действующую подписку сначала
   согласованно сверяют старый backlog с уже выполненными уведомлениями.
2. Один раз прочитай журнал этой подписки. Не ищи последнее сообщение в чатах
   вместо отсутствующего события. Прочитанный envelope содержит исходный eventId
   и payload и сохраняет прежние ограничения по тексту и доступу.
3. Обрабатывай записи по порядку. Для event=null обозначь gap_reason, не
   восстанавливай содержание догадками. Для обычного события примени правило
   пользователя и основной workflow skill. Уже подтверждённые события журнал
   повторно не возвращает; не отправляй уведомление отдельно из payload запуска.
4. После успешного разрешённого действия (либо учёта нерелевантности/пробела)
   вызови ack с receipt именно этой записи. Если действие не удалось, остановись
   и не подтверждай эту запись или более поздние. При ошибке курсора прочитай
   журнал снова; при неоднозначном результате доставки проверь канал, не повторяй
   внешнее действие автоматически. Повтор самого ack безопасен.
5. При has_more продолжи следующей ограниченной страницей после подтверждения
   текущей. При blocked_on_delivery закончи запуск без циклического опроса.
   Пустая страница не доказывает отсутствие сообщений в Zalo и не оправдывает
   поиск кандидата по времени.

Журнал и курсор переживают перезапуск, но не дают атомарной отправки уведомления
с checkpoint. Параллельные запуски или сбой после уведомления до ack могут дать
повтор: exactly-once не обещается. Если канал поддерживает idempotency key,
используй ключ правила/подписки/eventId. Подписки разных правил должны иметь
отдельные курсоры. Получение события и его восстановление не расширяют разрешение
на отправку сообщений, чтение истории или изменение подписки.

Если recovery tools недоступны, явно сообщи об отсутствии payload/механизма
восстановления. Не читай SQLite, токены или signing secrets ради обхода.
