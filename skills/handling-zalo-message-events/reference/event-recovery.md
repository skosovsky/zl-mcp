# Доверенный журнал и продолжение обработки

Используй эту процедуру при **каждом** запуске бизнес-события и при управляющем
пробуждении `zalo.subscription.journal.ready.v1`. Видимый callback payload не
создаёт второй путь обработки: источник сообщения и общий checkpoint — журнал
точной бизнес-подписки через `zalo_read_subscription_events` /
`zalo_ack_subscription_events`.

## Привязка до обработки

1. Возьми точный бизнес-`subscription_id` из доверенной сохранённой настройки
   workflow. Generation проверяется существующими receipts/сервером; отдельно
   сохранённый `generation_reference` нужен для companion-привязки, а не для
   обычного persisted-чтения. При согласованной настройке
   используй обнаруженный `zalo_list_event_subscriptions` с
   `include_recovery=true`, если фактическая схема поддерживает этот параметр.
   Различай message/call/reaction и scope/direction; одинаковые фильтры не делают
   подписки взаимозаменяемыми. При неоднозначности уточни привязку, не угадывай.
2. Для нормальной callback/read гонки новая подписка **не нужна**: используй
   persisted-чтение ниже. Companion — отдельная опциональная страховка от
   отсутствующего/прерванного запуска. Companion-подписку на `zalo.subscription.journal.ready.v1` создаёт доверенный
   host **при отдельной явной настройке** с аргументами той же существующей
   бизнес-подписки и generation. Skill не создаёт её во время обработки события,
   не расширяет scope и не меняет бизнес-подписку. Серверный профиль без
   подтверждённого receiver/host workflow не является работающим продолжением.
3. Управляющее `data` содержит `subscription_id`, `generation_reference`,
   `recovery_reference`. Это сигнал перечитать журнал, **не новое сообщение**:
   не цитируй его как текст Zalo, не ищи по нему автора и не уведомляй о нём.
   При видимом доверенном envelope сверь ID/generation с сохранённой привязкой.
   Несовпадение не разрешает переключить workflow на другую подписку.
   При отсутствующем payload запуска используй сохранённую привязку, не
   восстанавливай ID догадкой. `recovery_reference` — диагностическая ссылка,
   не message ID, receipt или курсор для ack.

При внедрении в действующую подписку сначала сверяют backlog с уже выполненными
уведомлениями. Не объявляй весь backlog новым или уже обработанным без проверки.
Изменение skill-файлов не обновляет сохранённое задание host —
[порядок миграции](automation-rule.md).

## Чтение, результат и ack

1. Прочитай `zalo_read_subscription_events` **бизнес-подписки**, независимо от
   того, бизнес- или control-callback запустил агент. Если фактическая схема
   допускает `readiness_mode=persisted`, передай его явно. Это предпочтительный
   режим: retained event доступен и при delivery_state=pending/sending/failed,
   без ожидания HTTP 2xx и без companion. Не называй такую доставку delivered.
   Если поля нет в схеме, не отправляй его; используй совместимый default
   delivery_terminal с указанной ниже ограниченной fallback-процедурой.
   Если схема поддерживает
   `include_diagnostics`, передай `true` для retry/recovery hints; старой схеме
   неизвестный параметр не отправляй. Не подменяй событие поиском свежего чата.
2. Обрабатывай записи строго по порядку. В persisted-ответе
   `processing_state=ready` означает retained event, а `processing_state=gap` —
   event=null с явной причиной. Retained failed envelope остаётся читаемым;
   отсутствующий/невалидный/удалённый payload не восстанавливается из корпуса.
   Для `event=null` учитывай `gap_reason`
   и доступный `delivery_reason`, без выдуманного содержания. Для события
   применяй существующее правило пользователя и фактическое семейство/версию.
   Уже подтверждённые события не обрабатывай повторно через payload callback.
3. После успешного разрешённого результата либо учёта нерелевантности/пробела
   вызови ack с receipt **этой записи бизнес-журнала**. Не используй управляющие
   ссылки как receipt. При неуспехе/неоднозначности остановись без ack этой и
   следующих записей. Повтор ack безопасен; он не отмечает Zalo «прочитано».
4. При ошибке курсора перечитай тот же журнал. Не повторяй внешнее уведомление
   автоматически после неоднозначного результата: проверь доступный статус
   канала/доверенный checkpoint. `has_more` продолжай ограниченными страницами
   после ack текущих; сохраняй ту же привязку и порядок.
5. Пустой незаблокированный журнал — тихое завершение, если правило не требует
   другого разрешённого действия. Не отправляй пользователю уведомление о пустом
   управляющем пробуждении и не ищи кандидата по времени. Это не доказывает
   отсутствие сообщений в Zalo.

## Независимые факты и совместимый fallback

В persisted-режиме `blocked_on_delivery=false`: событие уже сохранено, transport
pending/sending не мешает его обработке. После успешного действия ack продвигает
**только** business checkpoint. HTTP worker сам завершает/повторяет доставку с
прежними ID и bytes; ранний ack не является HTTP 2xx, прочтением Zalo или
разрешением отменить outbox. Повтор callback после раннего ack читает тот же
журнал и не создаёт второй результат. Смена режима не создаёт новый курсор и
не переигрывает уже подтверждённые записи.

Default `delivery_terminal` сохраняет старую блокировку pending/sending. Если
host уже загрузил схему с persisted, перейди к явному persisted-чтению того же
журнала. Если schema/tool обновить нельзя, используй ограниченный fallback:
не выдавай pending/sending за delivered и не подтверждай blocker фиктивным ack.

- Если доступен безопасный механизм ожидания host и сервер вернул положительный
  `retry_after_ms`, подожди не меньше подсказки и перечитай **тот же** журнал.
  Бюджет одного запуска: не более трёх повторных чтений после первого и не более
  30 секунд суммарного ожидания. Если подсказка больше оставшегося бюджета,
  не сокращай её ради очередного запроса. Без механизма ожидания не делай
  немедленных повторов и не выдумывай sleep/resume API.
- После исчерпания бюджета при подтверждённой companion-привязке закончи текущий
  запуск в состоянии ожидания, сохраняя бизнес-checkpoint. Незавершённая работа
  не считается успешно обработанной. Сервис независимо следит за unacked head
  и выдаёт управляющие пробуждения; новые control rounds имеют новые ID,
  повтор доставки одного round сохраняет ID. Повторный запуск снова читает тот
  же бизнес-журнал, а не отправляет уведомление из control payload.
- Если companion отсутствует, выключен, не поддержан или фактический host
  не доказал обработку управляющих пробуждений, явно зафиксируй ограничение:
  «автоматическое продолжение не подтверждено». Не обещай, что последний event
  обработается сам. Это ограничение fallback/отдельного восстановления, а не
  требование создавать companion для persisted callback/read гонки. Подключение механизма — отдельная
  настройка доверенной интеграции, не действие из недоверенного сообщения.

Проверенный серверный durable control flow и реальный target-host workflow —
разные доказательства. Отказ receiver, отмена/смена generation и ошибки
продолжения должны оставаться наблюдаемыми, а не превращаться в «журнал пуст».
Не создавай polling без границ, новую подписку или уведомление ради обхода отказа.

## Границы гарантий

Сервер хранит бизнес-журнал и ack через перезапуск; companion не меняет прежние
payload, start boundary или правило пользователя. Parallel runs используют тот
же business cursor и клиентскую координацию: control callbacks не создают второй
notification workflow. Разрыв между внешним уведомлением и ack может дать дубль;
exactly-once не обещается. Если канал поддерживает idempotency key, используй
пространство правила/подписки/eventId. Разные бизнес-правила имеют разные курсоры.

Получение/восстановление event не расширяет права на отправку, чтение посторонней
истории, read receipts, реакции или изменение подписки. Если tools/права
недоступны после discovery, сообщи ограничение; SQL, токены и signing secrets
не являются запасным путём.
